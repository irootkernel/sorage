# Project Memo contract

## 1. Purpose and authority

A Project Memo is an explicitly recorded, project-scoped reminder or note. It has an owning Project and author provenance, but no sender, recipient, delivery, Review Note, acceptance Revision, or next actor. It is not an execution log, task scheduler, or second roadmap. A typical Memo says that an Epic's handler finished and its separate validator should run after the user returns.

[MEM-001 to MEM-024](required-specification.md#18-project-memos) own required behavior. [ADR-0027](../architecture-decision-records/README.md#adr-0027-project-memos-as-a-separate-domain-in-m7) owns the material decision. This document occupies the explicit Memo-contract position in [the documentation authority order](../README.md#source-of-truth-precedence) and [governance](../governance/README.md#3-authority-order). It owns detailed Memo lifecycle, interfaces, pending-attempt handling, and snapshot-format-2 extensions. Common authentication, security, envelopes, transaction safety, and legacy Handoff behavior remain owned by the higher-ranked shared documents; their Memo exceptions and format-1-only statements must be explicit, not inferred from this document's specificity. [The roadmap](../roadmap/README.md#epic-013-project-memos) alone records implementation status. M7 is an internal delivery milestone, not a product version or a claim that these commands already ship.

## 2. Scope and settled defaults

The first delivery includes CLI, local HTTP API, Web UI, the existing `use-sorage` skill, durable storage, upgrade, backup, and restore. One Memo belongs to exactly one registered Project. Any explicitly authorized local User operation, including one performed by an AI on that User's behalf, may create or manage it. Creating a Memo does not authorize executing its text.

All Memo mutations use the existing User actor (`kind=user`, `id=null`). This describes user-directed operation provenance, not proof that a human typed the command. The Web and CLI use the same rule; `--as-user` remains an accepted redundant explicit declaration. There is no new account system, named-user profile, AI identity registry, per-author ownership rule, or Project-to-Project role matrix. Future author display names must not retroactively invent historical identity.

The following are excluded: hooks, automatic discovery, notifications, due dates, priorities, assignees, dependency graphs, `in_progress` or `blocked` states, comments, attachments, full text revision history, hard deletion, pinning, separate Memo archival, automatic Handoff conversion, automatic execution, roadmap inspection, and Codex, Aquarium, Podway, Dolgorae, or Gul runtime dependencies. Another computer does not automatically receive local Memos; backup/restore is not live multi-machine synchronization.

## 3. Model and invariants

| Field | Contract |
|---|---|
| `id` | Immutable UUID generated through the existing ID port. |
| `projectId` | Immutable foreign key to the existing Project UUID, not its path or display name. |
| `title` | Required, trimmed, nonempty single-line text, at most 200 Unicode scalar values and 800 UTF-8 bytes; reject control characters and unpaired surrogates. |
| `body` | Markdown text, default empty string, at most 65,536 UTF-8 bytes; preserve accepted Unicode and line endings exactly, reject invalid Unicode and NUL. An empty body is valid when the title carries the reminder. |
| `state` | Exactly `open`, `done`, or `dismissed`; creation uses `open`. |
| `rowVersion` | Positive safe integer beginning at 1; increments once per actual content or lifecycle change. No separate Handoff Revision counter. |
| `createdAt`, `updatedAt` | Existing UTC Clock timestamps; `createdAt` never changes. |
| `createdBy`, `updatedBy` | Existing User actor representation. |
| `closedAt`, `closedBy` | Both null while open; set to the latest closing operation's time and User actor in either closed state. Reopen clears both; prior transitions remain in metadata events. |

Duplicate titles and identical text are allowed. Only an exact idempotency key replay deduplicates creation. A Memo ID selects one object, not a title or the first search result. Moving a binding, losing a local directory, or changing a Project display name does not change Memo identity. M7 has no move-to-another-Project operation.

`done` records the caller's assertion that this reminder was handled. `dismissed` records that it is no longer needed, without asserting the work was performed. Neither establishes Epic acceptance, validation success, code correctness, a Git commit, publication, Handoff acceptance, or Podway completion. Text naming `EPIC-002` is ordinary text, not a foreign key or an executable instruction.

## 4. Lifecycle and concurrency

| Operation | Allowed state | Result |
|---|---|---|
| `add` | New object | Create `open`, version 1. |
| `update` | `open` | Replace supplied title and/or body, increment once if bytes change after title normalization. Omitted fields remain unchanged. |
| `done` | `open` | Set `done`, closing metadata, and increment once. |
| `dismiss` | `open` | Set `dismissed`, closing metadata, and increment once. |
| `reopen` | `done` or `dismissed` | Set `open`, clear closing metadata, and increment once. |
| Repeating `done`, `dismiss`, or `reopen` in its already-requested state | Matching current state | Success with `changed=false`; no version, timestamp, or event change. |
| Editing a closed Memo or switching directly between the two closed states | Closed state | `MEMO_NOT_OPEN`; reopen explicitly before making a different decision. |

Every update, done, dismiss, and reopen requires `expectedRowVersion` from an observed Memo. There is no force flag and no adapter-side read-latest-then-overwrite shortcut. Check the expectation before state validation and before deciding an operation is a no-op. A stale caller gets `ROW_VERSION_CONFLICT`, including when the requested state now happens to match. A missing expectation is invalid input. A version overflow fails without mutation.

Idempotency replay is checked before a fresh version/state check, after the current installation and User context and the submitted input are validated. A retained exact retry returns its originally committed receipt without executing again; it does not claim that the returned historical object is the current state. Recovery of an outcome-unknown attempt MUST use the replay-only mode in section 8.1, which never executes on a receipt miss. Required expected versions still identify the original request in this mode; do not refresh them to the current row. Refetch before issuing a genuinely new action. A new key is not permission to bypass a stale expectation or to silently repeat an uncertain operation.

## 5. Project selection and retirement

For CLI add and list, `--project <slug>` selects an existing Project without requiring a working binding or an accessible local directory. Without it, use the existing worktree-aware Project resolver for the current directory. An unregistered directory returns `PROJECT_NOT_FOUND` with guidance to select or register a Project; ambiguity returns `AMBIGUOUS_PROJECT`. Never infer a project from the Memo title, a recently used project, or an unregistered-workspace sender. `--as` is not an alias for `--project` on Memo commands; reject it and Handoff-only options rather than silently changing scope or actor.

Detail and existing-object mutations address the UUID directly. Optional `--project` is an assertion: a different owning Project returns `MEMO_NOT_FOUND` without changing anything. The HTTP detail routes apply the equivalent optional `projectId` assertion. Reads expose only local installation data under the existing same-OS-user trust model; this is not a new multi-tenant security boundary.

An archived Project remains readable. Existing Memos may be edited while open, marked done, or dismissed so retirement does not prevent cleanup. A new Memo or a state-changing reopen in an archived Project fails with `PROJECT_ARCHIVED`; read archive state in the same write transaction as the mutation. Repeating reopen on an already-open Memo is a no-op after the required version check and does not reopen retired work. An exact retained creation/reopen replay remains readable after archival without creating or reopening anything. An unbound but active Project supports explicit-ID/slug Memo operations because no Artifact source directory is needed. Archival does not cascade into Memo states.

## 6. Persistence and events

Extend the existing SQLite database, not the project filesystem or a new journal service. At the inspected baseline, migrations end at version 6; append the next unused migration and never edit old migrations. Add `project_memos`, Project and state/list indexes, and a nullable `memo_id` foreign key on `events` with a lookup index. A Memo event has `handoff_id=null`; its `memo_id` identifies the Memo. Existing event kinds and Handoff rows keep their meanings. Reconfirm the next migration number at Task start if the baseline moved.

Use existing core ports, synchronous UnitOfWork, SQLite WAL, busy timeout, and mutation fences. Core owns normalization, state transitions, and conflicts; adapters own SQL and transactions; CLI/HTTP call the same use cases. The Project check, Memo insert or compare-and-set, event append, and optional idempotency receipt commit in one write transaction. Do not perform filesystem I/O or `await` inside it. A rolled-back mutation leaves no row, event, or successful receipt. A process restart can read any acknowledged commit without a Codex session or daemon being alive.

Add exactly the metadata event kinds `MEMO_CREATED`, `MEMO_UPDATED`, `MEMO_MARKED_DONE`, `MEMO_DISMISSED`, and `MEMO_REOPENED`. Include Project ID, Memo ID, resulting row version, transition or changed-field names, actor, and UTC time. Do not put title, body, raw prompts, local paths, or full prior content in event metadata. Reads and no-ops append no events. Memo events never appear in `sorage events <handoff-id>` or change Handoff inbox/outbox counters or `.sorage/INBOX.md`.

Normal native startup recovery, including the existing pending-filesystem-intent drain, remains in force. Side-effect isolation means Memo domain operations do not introduce Handoff mutations; it does not disable already-owed recovery work. Tests must distinguish a Memo's own effects from a preexisting pending recovery obligation.

M7 retains current Memo content and metadata transitions, not every earlier body. Do not add a public Memo-event browser merely to justify the event ledger. Use existing backup disclosures to explain that earlier Git snapshots may retain older bodies and that dismissal is not erasure.

## 7. Read model and paging

`list` defaults to one selected Project and `state=open`. `--all-projects` is an explicit alternative to Project selection; it includes registered active and archived Projects, with archive status visible, and is incompatible with `--project`. `state=all` explicitly includes both closed states. A specified archived Project can always be queried. There is no implicit all-project discovery when the current directory fails to resolve.

Provide optional `query`, at most 200 Unicode scalar values and 800 UTF-8 bytes, as a literal case-sensitive substring of title or body. No regular expressions, SQL wildcard interpretation, Unicode normalization, roadmap parsing, or full-text indexing is required. An empty query is equivalent to omission. Bind it as data in parameterized SQL.

Use `createdAt DESC, id DESC`, so editing or closing a Memo does not move it between pages. This is the Memo-specific exception to the existing Handoff `updatedAt` order. Reuse `ui.defaultPageSize` and the existing validated list upper bound. The opaque cursor binds the Memo list namespace, installation, resolved Project ID or all-project scope, state, query, page size, and last sort key. Filter mismatch or malformed data returns `CURSOR_INVALID`. Cursors are not portable between Handoffs, installations, or necessarily upgrades.

Each page reflects its own database read snapshot. Changing state may change membership between pages; do not advertise cross-page snapshot isolation or a total that belongs to another snapshot. Clients restart traversal to refresh. Summary rows include ID, Project ID/slug/display name/archive state, title, state, row version, timestamps, and a bounded body preview. A preview truncates at a valid UTF-8 boundary, at most 512 bytes, and has an explicit `bodyPreviewTruncated` boolean. Detail includes the complete body and provenance/closing fields. Render names through the current Project join, not as Memo identity.

## 8. CLI contract

The following commands are new M7 commands, not aliases of `send`, `accept`, or `archive`. They use the existing success/error envelope and JSON-only stdout policy. Diagnostics go to stderr.

| Command | Inputs and result |
|---|---|
| `sorage memo add` | Required `--title`; optional `--project`; zero or one of `--body <text>` and `--body-file <path>`; optional idempotency key; return the created Memo receipt. |
| `sorage memo list` | Project selection or `--all-projects`, `--state open\|done\|dismissed\|all`, `--query`, `--limit`, `--cursor`; return summary page. |
| `sorage memo show <id>` | Optional Project assertion; return full detail, no mutation. |
| `sorage memo update <id>` | Mandatory expected row version; at least one title/body input; omitted values unchanged and explicit empty body clears it. |
| `sorage memo done <id>` | Mandatory expected row version; record handled status. |
| `sorage memo dismiss <id>` | Mandatory expected row version; record no-longer-needed status. |
| `sorage memo reopen <id>` | Mandatory expected row version; reopen without execution. |

`--body-file` imports text once, never attaches the file or maintains a live link. Require a regular readable file, enforce the byte bound before and during read, reject invalid UTF-8, and close the handle on every error. Do not accept a FIFO, device, socket, or implicit stdin. `--body` and `--body-file` are mutually exclusive by presence even when a string is empty. Reject a body from two sources. The User intentionally selects the file, so Handoff sender-root restrictions do not apply; this grants no bulk filesystem discovery. Empty imported content is valid. Do not trim or normalize body content.

Add/update/done/dismiss/reopen accept the existing UUID idempotency key convention. The operation namespace is Memo-specific and disjoint from Handoff operations. The shared application normalizes both CLI and HTTP inputs before hashing: resolve Project selectors to UUIDs, apply the specified title trimming, default an omitted creation body to the empty string, and preserve the distinction between omitted update fields and an explicitly empty body. The normalized hash includes operation, installation/User identity, resolved Project for creation or Memo ID and optional scope assertion, accepted title/body fields, and expected version for existing-object operations. JSON key order, JSON whitespace, equivalent string escapes, HTTP method/path spelling, authentication token, CLI argv spelling, and text-file pathname are not request identity. File content bytes, not `--body-file` versus `--body`, determine accepted body content. Do not trim, Unicode-normalize, or convert line endings in the body: changed body bytes are a different request, even when they render alike.

The common application and its transactional DB receipt are the sole Memo replay authority. For a retained valid receipt, the same key and normalized request return the first receipt; another normalized request conflicts. Reuse the existing 24-hour receipt retention and write-transaction exclusion; an exact replay does not extend the original expiry. Installation identity and elapsed client time do not prove receipt continuity across restore, expiry, or loss. Web callers must generate keys; the skill supplies one for retriable mutations. CLI key omission remains allowed only for ordinary execution and makes create deduplication the caller's responsibility. Refusals and rolled-back failures create no successful receipt; a committed no-op may have a receipt without a Memo event. An uncertain attempt is recovered only through the non-executing mode below.

Mutation `data` is `{memo: MemoDetail, changed: boolean, replayed: boolean}`. `show` returns `MemoDetail` as `data`. List `data` is `{items: MemoSummary[], nextCursor: string|null}` and makes no total-count promise. The original response has `replayed=false`; no-op receipts have `changed=false`. A DB replay preserves the original `memo` and `changed`, sets `replayed=true`, and does not refresh historical Memo fields from a current row. Each transport wraps this data in a new response with that invocation's `meta.requestId`; it does not replay the original complete HTTP envelope. Refetch the Memo before any new write.

### 8.1 Execution versus replay-only recovery

The five Memo mutation commands accept `--replay-only` together with a required `--idempotency-key <uuid>` and the original inputs, scope, and expected version where applicable. Without that flag the application mode is `execute`; with it the mode is `replay-only`. Reject replay-only without a valid key, or on list/show, as invalid input. The application receives mode separately from the normalized business request. Mode is not part of the request hash or receipt namespace: an execute receipt must match its replay-only lookup across CLI and HTTP. No new command or recovery service is introduced.

| Application mode | Matching unexpired receipt | Unexpired key with a different normalized request | No unexpired receipt |
|---|---|---|---|
| `execute` | Return the historical receipt with `replayed=true`; no new effects. | `IDEMPOTENCY_CONFLICT`; no effects. | Evaluate current state and the normal mutation contract; execution is allowed only as a new, explicitly intended operation. |
| `replay-only` | Return the historical receipt with `replayed=true`; no new effects. | `IDEMPOTENCY_CONFLICT`; no effects. | `MEMO_REPLAY_UNAVAILABLE`; never execute, create a receipt, or manufacture a no-op success. |

Receipt eligibility uses the server Clock sampled for the consistent lookup under existing storage/restore fences: only `expiresAt > now` is eligible, and equality is expired. Missing, expired, or restore-absent receipts all mean that the original outcome cannot be established, not that it failed. A storage error remains a storage error, never a miss followed by execution. Replay-only performs no Memo, event, or receipt write, reservation, expiry extension, or expiry cleanup; filter expired records instead of reusing a lookup that deletes them. Existing startup recovery remains separate as stated in section 6. A concurrent original request may commit after a replay-only miss, so that miss neither cancels it nor proves non-execution.

A client recovering from timeout, lost/malformed response, reload, or authentication recovery MUST use replay-only with the same key and request; it MUST NOT fall back to execute, replace the key, or infer success from a title/content match. This is true even within 24 hours and with the same Installation ID. Explicit replay-only inspection remains safe after suspected expiry because the server cannot execute on a miss. It requires valid original material and the intended Installation; a known different Installation is not an automatic recovery target. A result remains unknown until exact evidence settles it, or the user explicitly abandons further recovery without changing that outcome under section 10.1. Repeating an execute request after receipt expiry is not a safe recovery contract.

## 9. HTTP and error contract

Add these routes under existing `/api/v1` authentication, Host checks, request bounds, JSON parsing, and response-security policy. Neither endpoint existence nor a Memo lookup may bypass authentication.

| Method and path | Contract |
|---|---|
| `GET /api/v1/memos` | Required `projectId` or `allProjects=true`, mutually exclusive; optional state/query/limit/cursor. No server working-directory inference. |
| `POST /api/v1/memos` | JSON `{projectId, title, body?}`. Create under the User actor. |
| `GET /api/v1/memos/{id}` | Full detail; optional `projectId` assertion. |
| `PATCH /api/v1/memos/{id}` | JSON `{expectedRowVersion, title?, body?, projectId?}`; at least one content field. |
| `POST /api/v1/memos/{id}/done` | JSON `{expectedRowVersion, projectId?}`. |
| `POST /api/v1/memos/{id}/dismiss` | Same request shape; distinct lifecycle operation. |
| `POST /api/v1/memos/{id}/reopen` | Same request shape; distinct lifecycle operation. |

The HTTP responses use the same data shapes as the CLI inside the existing envelopes, with success status 200 for these routes. `Idempotency-Key` maps to the same application receipt contract across transports. Reject unknown Memo request fields, client-supplied state/provenance/IDs/timestamps, null in place of strings, unsafe integer versions, contradictory scope, and unsupported methods. Enforce a 512-KiB encoded JSON request cap while collecting raw byte chunks and before decoding or whole-body parsing; enforce decoded text bounds independently. No multipart upload or Artifact route is introduced.

For the five mutation routes, the optional `Idempotency-Mode` header accepts exactly `execute` or `replay-only`; omission selects execute. Replay-only requires a valid `Idempotency-Key` and the same normalized JSON values, path target, and optional Project assertion as the original request; equivalent JSON serialization may differ. Reject unknown, duplicate, combined, or empty mode values, missing/invalid replay-only keys, and mode headers on Memo GET routes with `MEMO_INVALID_INPUT`. Bind mode into the common application before dispatch, not into the semantic request hash. The header adds no endpoint, authentication bypass, or HTTP cache. A successful replay-only response has `replayed=true`; an unavailable receipt returns the typed error below without invoking a write path. Existing Handoff handlers do not gain this mode.

Memo JSON bodies MUST undergo fatal UTF-8 decoding before JSON parsing, application normalization, request hashing, or receipt lookup. Collect the bounded raw bytes and decode once with a fatal decoder, such as `TextDecoder("utf-8", { fatal: true })`; do not use replacement decoding through `Buffer.toString("utf8")`, request-stream string encoding, or per-chunk independent decoding. Valid multibyte sequences split across HTTP chunks remain valid; a truncated sequence at end-of-input is an error. Map malformed UTF-8 to `MEMO_INVALID_INPUT` with HTTP 422, with no Memo mutation, event, receipt insertion/update, or successful replay. Do not echo request bytes or content in diagnostics. Byte-limit overflow remains `MEMO_TOO_LARGE` with HTTP 413.

The current `readDomainJsonBody` in `apps/daemon/src/domain-routes.ts` decodes with replacement and falls back to an empty object after parsing errors; it cannot satisfy this Memo input contract unchanged. Use a Memo-specific bounded strict reader, or an explicitly selected strict mode whose existing callers retain their behavior. Do not silently change the shared reader for Handoff or other legacy routes. Invalid JSON or a non-object Memo request must also fail with `MEMO_INVALID_INPUT`, not become an empty request. After JSON parsing, retain scalar-value validation so escaped unpaired surrogates such as `\uD800` or `\uDC00` are rejected even though their request bytes are valid UTF-8.

A deliberately supplied Unicode replacement character U+FFFD is valid data. Accept its valid UTF-8 encoding `EF BF BD` and equivalent JSON escape `\uFFFD` under the usual field rules; do not reject a request merely because its decoded text contains that character. Invalid bytes such as `FF` must never be repaired into U+FFFD, stored, or treated as a replay of valid U+FFFD input. Reusing an already committed key does not bypass decoding or input validation. A rejected malformed request must neither create a receipt for a fresh key nor alter an existing receipt.

Memo route registration MUST bypass the legacy transport replay wrapper in `apps/daemon/src/server.ts` and `apps/daemon/src/route-kit.ts`. In the current router, leave `RouteEntryInternal.idempotent` unset or false for Memo routes; that flag enables the raw-body spool/hash and process-local response cache, not application idempotency. Use the ordinary authenticated handler branch, which already passes `idempotencyKey`, and call the shared Memo application after bounded parsing and validation. Do not call `evaluateIdempotency`, `storeReplay`, or `discardReplay` for a Memo request, introduce another Memo response cache, or hash a raw HTTP body as its semantic identity. Keep existing Handoff route registration, upload spooling, replay behavior, and response goldens unchanged.

The required order is Host validation, authentication, route/method validation, bounded raw-byte collection, fatal UTF-8 decoding, JSON parsing and field/Unicode validation, application normalization, then mode-aware receipt lookup and, only in execute mode, possible execution under the shared transaction contract. Request-size and strict-decoding enforcement remain mandatory even when a key might replay; bypassing the legacy wrapper must not bypass authentication or input limits. TASK-091 must prove malformed raw-byte rejection without side effects, valid U+FFFD and split-multibyte acceptance, matching semantic JSON with different serialization replaying with `replayed=true`, same-key body changes conflicting, HTTP/CLI cross-replays using the same receipt, and a dropped response followed by daemon restart producing no second row or event.

| New code | HTTP | CLI exit | Meaning |
|---|---|---|---|
| `MEMO_NOT_FOUND` | 404 | 66 | Unknown Memo or failed optional Project assertion. |
| `MEMO_INVALID_INPUT` | 422 | 64 | Malformed UTF-8 or JSON, invalid fields/Unicode, missing expectation, unsupported Memo option combination, or unsafe row version. |
| `MEMO_TOO_LARGE` | 413 | 65 | Encoded request, decoded body, or bounded file input exceeds its limit. |
| `MEMO_NOT_OPEN` | 409 | 65 | Editing a closed Memo or choosing the other closed state without reopen. |
| `MEMO_REPLAY_UNAVAILABLE` | 409 | 75 | Replay-only found no unexpired receipt; original outcome remains unknown. No automatic execution or new-key recovery is permitted. |

Reuse `PROJECT_NOT_FOUND`, `PROJECT_ARCHIVED`, `AMBIGUOUS_PROJECT`, `ROW_VERSION_CONFLICT`, `CURSOR_INVALID`, `IDEMPOTENCY_CONFLICT`, `SERVICE_PAUSED`, authentication, and storage errors. Extend the shared row-version error description to include Memos without changing existing Handoff error output. A missing flag caught by CLI parsing retains usage exit 2; application-level invalid input uses the table above. File-open failures use the existing filesystem error category and never fall through to empty content. Contract tests pin every new mapping and verify existing Handoff goldens remain unchanged.

## 10. Web behavior

Implement the Memo view in the shipped browser assets owned by `apps/daemon/src/web-app.ts`, served by `apps/daemon/src/server.ts`. At this design baseline `apps/web/src/index.ts` is a stub, not the production frontend. Reuse the current navigation, API helper, and `renderMarkdownSafe` path, with Memo-specific bounded request handling and the pending gate below. M7 does not move the frontend to `apps/web`, add a framework, or introduce a second asset pipeline. Test the assets that the actual daemon serves, not a disconnected stub or a new demo.

Add Memos as a separate Project view beside Handoffs. A selected Project opens its open Memos by default. A separately explicit all-project view is available; show Project name on every row. State filters are Open, Done, Dismissed, and All. Rows show title, preview, state, and updated time; detail shows full sanitized Markdown and provenance/timestamps. Provide plain-text title/body editing, a read-only preview, and a visible character/byte-limit error. Do not add a sender/recipient picker or an Accepted button.

Create, Save, Mark done, Dismiss, and Reopen are explicit user actions. Done and Dismiss need no destructive-delete confirmation because they are reversible. Closed content is read-only until Reopen. Keep the current draft on conflicts and transport failures, refetch authoritative state, and require a new explicit action to apply against a newly observed version; never silently overwrite or mark done from an unseen version. A successful application receipt, not optimistic painting, confirms a mutation. A historical replay confirms the original outcome, not current Memo state.

Before the first execute dispatch of a Web mutation, acquire one tab-wide Memo write gate and persist one bounded active pending-attempt record in session storage: a local format version, server/Installation identity, operation, exact accepted input, Memo/Project identity, expected version where applicable, original idempotency key, and first-attempt time. Recovery of any retained attempt uses replay-only, including when a crash occurred after local persistence but before dispatch; an unavailable receipt does not authorize automatic execute. The gate covers every Memo and Project in that tab, not just the originating button, form, or selected Memo. Refuse to send when storage is unavailable, full, malformed, or cannot preserve the record; keep the draft and show a recovery error. Memo A's active record MUST NOT be overwritten by a Memo B request. Only settlement or the explicit abandonment transition in section 10.1 can release this gate.

While an outcome-unknown attempt remains active rather than explicitly abandoned, disable all new Memo writes in that tab and enforce the same gate at the common Memo-submit function before any network call. Reading, searching, pagination, navigation, and draft editing remain available. Navigating to another Project or Handoff view must not clear the gate. Other tabs and CLI clients remain independent and rely on server compare-and-set and transactional receipts; this is not a global writer lock. Serialize explicit exact retries too, so at most one request for the retained identity is in flight. An old callback may settle only its matching key and Installation, never a later record.

After reload or authentication recovery, restore the active pending gate before enabling writes, show the retained request, and use `Idempotency-Mode: replay-only` for every explicit recovery dispatch. Never refresh the first-attempt time, expected version, or key. Same Installation ID after restore does not prove that receipts survived, and a client-side 24-hour check is not an execution fence. Expired or uncertain client time may still permit a valid replay-only inspection; the server decides receipt eligibility and never executes on a miss. Missing/invalid original material or a known different Installation prevents dispatch and leaves the outcome unknown; offer read-only investigation and explicit abandonment rather than reconstructing a request. Session storage supports same-tab reload, not guaranteed recovery after tab closure, browser data removal, or every browser restart; disclose that limit separately from server Memo durability.

| Pending disposition | Gate and retry-material rule |
|---|---|
| Valid receipt for the exact retained operation/key and Installation | Remove that pending record, release the gate, and refresh current Memo data before any new write. If removal fails, keep writes blocked and show a local-storage recovery error. |
| Confirmed non-execution of the original attempt | Release the gate only after removing its record; preserve the draft and show the refusal. A validated non-mutating rejection of the first and only dispatch, with no previous transport ambiguity, is such evidence. |
| Timeout, abort, disconnect, malformed response, or ambiguous server failure | Keep the original record and gate. An error received on a later retry is not by itself proof that the first attempt did not commit. |
| `MEMO_REPLAY_UNAVAILABLE`, receipt expiry, or other unresolved outcome | Keep the warning and active gate by default. Offer replay-only inspection where possible or explicit abandonment under section 10.1; no execute fallback, replacement key, or title-based deduplication. |
| Explicitly confirmed abandonment of further recovery | Preserve an outcome-unknown notice and retire the active request locally before releasing the gate. Do not classify the original operation as failed, successful, or cancelled. |

A new request is a separate explicit user action after settlement or recorded abandonment; do not queue it behind the uncertain one. Abandonment never submits a replacement request. Keep pending content and keys out of logs, constrain retained text by the Memo input bounds, and disclose temporary browser-local retention. This record is retry material, not a Memo authority or an execution journal.

Use the existing safe Markdown renderer. Disable raw HTML and unsafe URL schemes and do not introduce automatic remote-image fetching from Memo bodies. Render titles and previews as text. Loading, empty, validation-error, disconnected, conflict, and archived-Project cases have distinct visible states. Include keyboard access, associated labels, visible focus, responsive layout, and Korean IME/newline round-trip checks. Memo changes never refresh or mutate Handoff state as a hidden side effect.

### 10.1 Abandon recovery without asserting an outcome

Provide an explicit `Abandon retry and continue` action for the retained attempt. Show its Project, operation, title or target ID, original key, and an outcome-unknown warning. Require confirmation that the original may already have committed or may finish later, that this action does not cancel or delete server work, and that repeating the same intent as a new request can duplicate effects. This is available after restore, expiry, or any other unresolved response, not only after a fixed time limit. It is not Memo dismiss/done, a retry, a server mutation, or a positive completion report.

Keep one active pending record plus a bounded collection of passive abandoned-attempt notices in the same versioned per-tab session-storage record. Each notice retains server/Installation, original key, operation, Project/known Memo ID, expected version if any, title, first-attempt time, abandonment time, `outcome=unknown`, and `retryDisposition=abandoned`; omit the body and executable retry payload. Limit the collection to 32 notices and never evict silently. At capacity, let the User inspect/copy and explicitly remove an older browser-only notice with a retention warning before another abandonment; removing a notice changes no server state or original outcome. This collection is not a submission queue, is never replayed, and has the same temporary session-storage lifetime as the active record.

Persist addition of the notice and removal of the matching active record in one replacement of that storage value, then release the in-memory gate. A failed save leaves the active record/gate unchanged. Reload reconstructs only an active attempt as blocking; abandoned notices remain visible but nonblocking. Each callback checks Installation, key, and active/abandoned disposition: a late response for A must never clear B's pending record, enable B's controls, submit A again, or paint A's outcome as B's. Exact late evidence may be associated with A's notice only; it cannot reactivate recovery. Aborting or detaching a local fetch during abandonment is not evidence of server cancellation.

After abandonment, clear automatic retry selection and require a fresh user action with a new key for any genuinely new intent. Do not pre-submit or silently convert the abandoned payload into that action; existing-Memo writes still require a freshly observed version. The old warning remains visible and distinguishes continuing with unrelated work from knowingly requesting a new operation. Unreadable or malformed storage remains an explicit local-storage recovery problem, not permission to discard unidentified requests silently.

## 11. Backup, restore, upgrade, and rollback

Keep the operational body in SQLite. Export Memos into Git snapshots, not standalone live Vault Artifacts. Snapshot format is independent of product SemVer, database migration number, and the Vault marker version. The shared [backup file catalog](interfaces-and-operations.md#26-backup-content) and [serialization rules](interfaces-and-operations.md#27-backup-algorithm-and-snapshot-determinism) distinguish these two generations explicitly:

| Snapshot generation | Inventory and manifest |
|---|---|
| Format 1 | Existing Project/Handoff snapshots and `events.jsonl`; manifest fields are `formatVersion: 1` and `counts` with projects/handoffs/events/artifacts. No Memo shard, `counts.memos`, `memoDigests`, or Memo event association. |
| Format 2 | Retain those families, add Memo shards, and add nullable `memoId` to every event row. Manifest has exactly `formatVersion: 2`, `counts` with projects/handoffs/events/artifacts/memos, and `memoDigests`. Counts are nonnegative safe integers. `memoDigests` is a string-to-string map covering every current Memo shard exactly once. |

A Memo snapshot contains exactly the fields in section 3, including original actor/closing metadata and the stable `projectId`; all fields are present, with explicit nulls for open closing metadata. Do not serialize list-only Project names, archive badges, previews, transport receipts, or export timestamps into a Memo shard. A Project rename changes its exported Project row, not the Memo snapshot. Format 2 always emits `counts.memos` and `memoDigests`; with zero Memos they are `0` and `{}`, and the `memos/` directory may be absent or empty but must contain no files.

### 11.1 Canonical bytes, digest, and path identity

- The shard filename is the canonical lowercase, hyphenated Memo UUID plus `.json`; the shard directory is that UUID's first two hexadecimal characters. Its Vault-relative location is `snapshots/memos/<xx>/<memo-id>.json`.
- `memoDigests` keys are relative to the `snapshots/` directory containing `manifest.json`, for example `memos/ab/ab000000-0000-4000-8000-000000000001.json`. Keys never include a leading `snapshots/`, an absolute path, backslashes, empty/dot/parent segments, percent-decoded aliases, or another shard spelling. Parse and validate the UUID encoded in the map key without filesystem access, derive its permitted canonical key, and require exact equality before joining paths. After a bounded read, require the snapshot record's UUID to match that key UUID. Reject symlinks and special files; verification must not read outside the snapshot root.
- Serialize each Memo with the existing `canonicalJson` convention in `packages/core/src/backup-snapshot.ts`: recursively sort object keys using the existing key comparator, keep array order, use JSON string escaping and two-space indentation, encode as UTF-8 with no BOM, use LF formatting, and append exactly one final LF. Do not normalize strings or rewrite the stored body. A CRLF in the body remains JSON-escaped CRLF, distinct from the file's LF formatting.
- The digest is SHA-256 of the entire serialized file's exact UTF-8 bytes, including its final LF. Store exactly 64 lowercase hexadecimal characters with no `sha256:` prefix. Compute and publish the digest from the same bytes written for that shard, not a second independently serialized object.
- Verify the digest against the raw file bytes before semantic import. Do not hash a parsed-and-reserialized object as a substitute; whitespace changes, BOM insertion, or removal of the trailing LF must fail against the original digest. Also require canonical bytes and the closed Memo schema, so a file with a recalculated digest but a noncanonical representation is still rejected. These hashes detect integrity mismatches; an unsigned manifest is not proof of authorship.
- Canonically serialize the format-2 manifest with the same JSON convention, sorting `memoDigests` keys deterministically. The map's exact key set, actual regular Memo files, valid distinct Memo IDs, and `counts.memos` must agree. Reject duplicate JSON object keys, duplicate IDs, missing or extra files/map entries, wrong shards, and invalid digests before import; do not let JSON parsing silently discard a duplicate manifest key. The required golden fixtures pin both canonical bytes and independently calculated expected hashes, rather than deriving all expectations through the production serializer.

### 11.2 Versioned verification and recovery

The new reader accepts format 1 as an installation with no Memos and maps old event rows to `memoId=null`. Preserve format-1 parsing and historical bytes; do not require format-2 fields in a legacy backup or silently treat Memo files/metadata under a format-1 declaration as supported data. It accepts format 2 only when every declared Memo, Project reference, closing-state invariant, row version, event reference, count, path, and digest is valid. A Memo event must identify an existing Memo and its owning Project and have no Handoff association; other event kinds have `memoId=null`. Other snapshot families retain their existing verification contract. Unknown newer formats fail closed. A corrupted Memo may not be silently skipped to produce a successful partial restore.

Restore all Memo rows and their metadata events with original UUIDs, versions, timestamps, and actor values; never regenerate them from titles or event guesses. Validate the full snapshot before mutation, import under the existing restore fence, and preserve rollback guarantees. Existing `RESTORE_TARGET_NOT_EMPTY` and installation adoption semantics remain. The new writer writes format 2 only after storage and backup support are implemented together, before CLI/API expose Memo mutation. Do not advertise backup success while leaving Memo rows unexported. Backup verify and restore dry-run enumerate and validate Memos, not only Artifact files.

Both snapshot formats exclude operational idempotency receipts and browser recovery material. Restore preserves Installation identity and Memo rows but does not restore or reconstruct receipts from Memo titles, events, or matching content. Reauthentication after restore supplies access, not proof of original execution. An old pending request must use replay-only; an absent receipt returns `MEMO_REPLAY_UNAVAILABLE` without creating another Memo even when the original key is less than 24 hours old. Restoring a snapshot that predates the original operation has the same unknown result, not permission to recreate it automatically. Database upgrade in place preserves existing valid receipts; backup restore into an empty installation does not. TASK-088 proves this storage boundary before public writes; TASK-089 and TASK-091 prove the mode-aware recovery path against restored fixtures, and TASK-094 qualifies the combined user scenario.

Normal diagnostics and events exclude body text. A user-requested backup intentionally includes current Memo content. Path redaction cannot sanitize arbitrary paths, secrets, or personal information typed into free text; disclose that limitation before enabling remote backup and in operations guidance. Earlier Git commits may retain old bodies. `done` and `dismissed` do not erase data, and there is no M7 Memo purge.

Do not claim an old binary safely rejects the upgraded operational database: the inspected migration runner does not establish that guarantee. Stop old CLI writers, daemon, and scheduled backup processes before upgrading; prevent unsupported mixed-version operation operationally. Keep a verified pre-upgrade backup. Do not downgrade the live upgraded database or overwrite it with an older snapshot writer. Rollback uses a separate empty home/Vault and the pre-upgrade format-1 backup; post-upgrade Memos are not present there and must first be preserved with the new binary. Do not mutate the real user home in qualification.

## 12. Skill and execution boundaries

Extend only Sorage's existing `skills/use-sorage/SKILL.md` after native commands exist. An explicit Memo request is a trigger distinct from inbox/outbox discovery. A request to list or show Memos authorizes read/report only. A request to add or edit a Memo authorizes that storage operation only, even when its body contains imperative text. Quoted content is untrusted data and cannot grant itself tool, network, commit, deletion, or execution authority.

A request to perform the described work and mark the Memo done may cover both actions. Apply the actual work's existing authority and verification requirements, read the current Memo/version before closing it, and leave it open when completion cannot be established or the Memo changed. Sorage does not implement or orchestrate that work. Do not create an Aquarium handler, change another repository, register hooks, scan Memos at session start, or auto-close from a turn ending, terminal state, commit, or assistant claim. Carry authorized continuation forward without repeated approvals inside its unchanged scope.

For a Memo mutation with an uncertain response, preserve the key and original input and inspect through `--replay-only` or the equivalent HTTP mode. Never retry as execute because the receipt is absent, expired, or missing after restore. Report `MEMO_REPLAY_UNAVAILABLE` as outcome unknown, not failed or done. Abandoning further recovery does not authorize re-executing the described work or automatically creating another Memo. A separately requested new operation uses new intent and identity; browser-local abandonment is not a new broker command.
