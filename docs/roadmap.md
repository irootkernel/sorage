# Roadmap

This roadmap plans the Sorage MVP as three milestones with independent release gates, under the governance fixed by ADR-0019 in [architecture-decisions.md](architecture-decisions.md).

It sits below [required-specification.md](required-specification.md), the accepted decisions in [architecture-decisions.md](architecture-decisions.md), [domain-and-architecture.md](domain-and-architecture.md), and [interfaces-and-operations.md](interfaces-and-operations.md) in the authority order of [sot-governance.md](sot-governance.md); where this roadmap disagrees with any of them, they win and this file is corrected.

## 1. Execution policy

Delivery is sequential with exactly one review overlap, and the rules below are the operational half of ADR-0019.

- At most one Task may be `In Progress`, and at most one other Task may be `In Review`.
- A second `In Progress` Task is not allowed; the overlap exists so that a review session can run beside an implementation session, not so that two Tasks can be implemented at once.
- The Task in `In Review` MUST reach `Completed`, `Blocked`, or `Deferred` before a third Task leaves `Planned`.
- A `Blocked` Task records its blocker, its owner, and its dependency impact on its own row before any other Task starts.
- A `Blocked` Task does not prevent a dependency-safe Task from starting, and it returns to `In Progress` only when no other Task is `In Progress`.
- Epic status is advanced by the Aquarium epic handler when every Task in the Epic's range is terminal, meaning `Completed` or `Deferred`; it is never edited ahead of its Tasks.
- Epic and Task identifiers become immutable once committed to this repository (GEN-012).
- A Task becomes `Completed` only when its acceptance gate has been observed to pass, never on a percentage or a summary.
- The Task start checklist and the Definition of Done tiers Chore, Standard, and Contract live in [sot-governance.md](sot-governance.md) sections 8 and 9; a Task whose deliverable begins with `Chore:` is closed under the Chore tier.
- Work discovered by an audit or a journey Task becomes new Tasks appended to `EPIC-009` before the release it blocks, so that a finding always has a slot and never expands the Task that found it.

## 3. Identifier policy

- Epic identifiers MUST use the globally unique form `EPIC-NNN`, beginning at `EPIC-001`.
- Task identifiers MUST use the globally unique form `TASK-NNN`, beginning at `TASK-001`.
- Numeric components MUST be zero-padded to three digits.
- Task numbering is global and MUST NOT restart inside an Epic.
- Identifiers are immutable once committed and MUST NOT be reused after completion, deletion, cancellation, or deferral (GEN-012).
- Titles, deliverables, and gates may change; the identifier does not.
- Every dependency MUST use a complete canonical identifier, and a range such as `TASK-009` to `TASK-012` is inclusive.

## 4. Status legend

| Status | Meaning |
|---|---|
| `Planned` | Defined but not started |
| `In Progress` | The one Task currently being implemented |
| `In Review` | Implementation is complete and under review by a separate session |
| `Completed` | The acceptance gate passed and documentation is current |
| `Blocked` | Work cannot proceed; blocker and next action are documented on the row |
| `Deferred` | Deliberately moved outside the current delivery scope |

These six words are the complete vocabulary and are case-sensitive.

## EPIC-003: Project registry and identity

- **Status:** Completed
- **Milestone:** 0.1
- **Objective:** Give every actor a stable identity and a correct resolution rule, including many bindings per Project and worktree folding, delivering the journeys AJ-03 and AJ-05.
- **Validation record (whole-epic review, 2026-08-25):** the whole-epic review over `20b5a6c` to `c2bfda5` converged at the first round with complete coverage, `ci_decision=pass`, and zero findings. `make test` exits 0 with 218 tests and `scripts/sot-check` exits 0 on the audited snapshot; the journeys AJ-03 and AJ-05 pass through the registry, resolution, and diagnostics surface this epic ships, with the send-dependent steps exercised through the eligibility and identity services until the Handoff commands arrive in `EPIC-005`. Every member task closed with a clean committed round-1 Mulgae run and no hardening deferral; nothing was pushed, and publication remains local.
- **Cold-validation remediation and accepted risk (2026-08-25):** the independent cold validation of this epic confirmed and remediated three defects with regression coverage: `project unbind` could not remove a binding whose directory had vanished, because the registration-time existence requirement also guarded unbinding, so unbind now matches the recorded binding directory through its longest existing ancestor and the `bindings.exist` recovery names that path; slug case-insensitivity folded only ASCII, so explicit slugs are now stored case-folded, making uniqueness and lookup Unicode-aware per PRJ-005; and every SQLite no-row guard read only `undefined`, which is `node:sqlite`'s shape, while the shipping `bun:sqlite` engine returns `null` and the vitest alias hides the difference, so `project unbind` and every unknown-slug lookup failed with `INTERNAL_ERROR` in the compiled binary, and the guards now treat both shapes as absence behind a spawned-Bun-runtime regression test. One low-severity risk is accepted: the Source of Truth does not define binding a bare Git repository, and the workspace-root derivation assumes the stored git common directory has a parent working tree, so `EPIC-005` must settle bare-repository binding semantics before the downgrade guard ships with `send` (PRJ-019).
- **Accepted risk (cold validation, 2026-08-26):** the second independent cold validation of this epic accepted one low-severity risk: the resolution-time `AMBIGUOUS_PROJECT` branch is unreachable in production, because two distinct same-depth stored directories can never both prefix-match one canonicalized query path and `UNIQUE(installationId, directory)` forbids duplicate stored directories, so a real firmlink or bind-mount alias is reported only by the `doctor` `bindings.ambiguous` warning while each spelling resolves to its own Project, although section 22.2 step 6 of [domain-and-architecture.md](domain-and-architecture.md) and the `bindings.ambiguous` catalog row describe resolution itself as able to raise this error. The finding lands as a new Task appended to `EPIC-009` before the 0.3 release, which must either compare stored directories physically at resolution time or amend the Source of Truth to scope ambiguity detection to `doctor`.

## 8. Epic completion and change rules

An Epic is complete when every Task in its declared range is `Completed`, or when a `Deferred` Task in that range has an accepted architecture decision and a matching update in [traceability.md](traceability.md).

No Epic is ever declared complete from a percentage, and the Aquarium epic handler performs the transition rather than a manual edit.

Tasks may be reordered only among dependency-safe Tasks and only with the reason recorded on the moved rows; the active-slot rule of section 1 always holds.

A new Task appended to an Epic takes the next unused Task identifier globally, never an identifier reclaimed from a `Deferred` or removed Task.

A change to a Task's cited requirements, milestone, or acceptance gate is a material change under section 4 of [sot-governance.md](sot-governance.md) when it moves scope between milestones.
