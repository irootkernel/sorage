## Native Channel and read-only client observations

A fresh main and two separate workers used native Codex CLI 0.164.0, `gpt-6.1-sol`, high reasoning, fresh HOME/CODEX_HOME directories and copied shipped resources. All three ran `codex exec -s read-only` with per-invocation Sorage MCP. Main approved only create/add/ack through the native per-tool configuration; each worker approved only post. Product annotations remained unchanged and no global registration occurred.

Main completed one continuous session: create, register both workers, wait for their reports, read them and separately acknowledge their actual sequence numbers. The relay request arrived as sequence 1 and the hostile report as sequence 2. Main declined the false approval/relay and tool/network/commit/deletion instructions while preserving sender attribution. Its fifteen MCP calls included bounded waits; each worker made one successful post, for seventeen calls in total. Each participant's only shell calls read the complete copied entrypoint and Channel reference. All three exited zero, with no provider error or repost. The final Channel stayed open with two messages and none unhandled; protected files and resource hashes were unchanged. A separate Channel retained its original unhandled sentinel. That fixture was prepared after main started and before either worker posted.

A separate fresh Codex client then reproduced reads under `codex exec -s read-only`, with per-invocation MCP and no write-approval override. Its four actual calls were Memo show, Channel messages, Handoff get and another Channel messages read, each with the existing recipient workspace as `cwd`. It made no shell call or mutation and exited zero. The full 208-entry home/Vault inventories were equal before and after, including file bytes, permissions and modification times; access times are not part of that claim. The returned Handoff metadata, exact Memo text and Channel bodies/handled states matched native state.

These observations cover the selected Codex family and native configurations, not current Claude compatibility, installed-global consumers or a provider airgap. TASK-125's earlier worker-capacity failure remains recorded separately; the successful new run does not erase it.

## Native v0.1.2 upgrade, restore and rollback

The old executable was rebuilt with Bun 1.4.2 from corrected tag object `2fd51e2732ee17d3157271c92c5efbe54f0220be`, commit `8c49b96e0f65c7c13062e97a3e9b30544536d78b`. Native frozen-lockfile dependency preparation used only the archived old workspace packages. Its unsigned SHA-256 exactly matched the previously documented `bd0e556d8145824dc6414738cf97b080d8bc3dd516ec41eee916c9a7a5b1f6f6`. This is a qualified tag rebuild, not a comparison with hosted release bytes.

Every product invocation selected a temporary SORAGE_HOME and physical TMPDIR. No daemon, service installation, scheduling or remote push was enabled. The old producer created two Projects, two Handoffs and two Memos, including an 80,006-byte BOM/CRLF file and a closed Memo. Its backup and verification succeeded. A retained pre-upgrade Vault copy supplied a separate old-binary dry-run and actual restore; original domain rows and Artifact bytes matched, schema 7 and foreign keys were intact, and operational receipts and bindings were absent as specified. Restored files were checked with `vault verify`; `backup verify` requires a snapshot export in the selected target and is not a substitute for that check.

The new executable reported `upgrade_required` at exit 78 without changing the complete home/Vault bytes, modes, modification times or inventory. One explicit `backup run` performed migrations 8 through 11, after which preflight reported `compatible`, the database named `11 / channels-v2`, and backup/Vault verification succeeded. The original seven migration entries, Project and binding identities, Handoff rows, original receipt strings, event metadata and stored body bytes survived; foreign-key and content-representation checks were clean. Original-key replay-only calls returned the retained Handoff and Memo results, including the historical open Memo receipt while the current Memo was done.

Comparisons use stored pre-upgrade data and the matching old reader, rather than a creation response: the old producer's persisted Memo did not contain the leading BOM present in its creation receipt. The new reader matched that stored baseline. The original file-backed Handoff retained its BOM/CRLF bytes, and newly accepted large Memo and Channel bodies preserved their leading BOM, CRLF and lack of a final newline.

After upgrade, a new inline Handoff had `storageKey: null`; a new large Memo and a Channel with small/large messages exercised the new representations. A second backup exported format 3 with three Handoffs, three Memos and the closed Channel. A separate dry-run and actual restore preserved public identities/views, exact body bytes, Channel name/handles/sequences/handled notes and closed state. Its 21 exported events matched the restored ledger field by field, including parsed metadata under the normal backup redaction, plus the two required restore audit events. Bindings and receipts initially remained absent; two explicit fixture bindings were subsequently added for original-context replay checks, which returned `HANDOFF_REPLAY_UNAVAILABLE` and `MEMO_REPLAY_UNAVAILABLE` at exit 75 without execution or replacement keys.

A distinct post-upgrade rollback used the retained old backup and matching old executable in another fresh home/Vault. It restored the exact old domain rows and file bytes at schema 7, with the eleven exported events plus the two restore audit events, no bindings or operational receipts, and none of the later-created data. The upgraded home was preserved, and the old executable never opened it. These are native process/file drills, not physical crash or power-loss tests.
