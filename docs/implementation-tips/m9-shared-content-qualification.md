## 1. Scope and owners

TASK-106 delivers the first common shared-content infrastructure of [ADR-0030](../architecture-decision-records/README.md#adr-0030-agent-communication-channels-and-shared-content-storage-in-m9) with no domain adoption: the pure content model and port in `packages/core/src/content.ts`, the SQLite/filesystem store in `packages/adapters/src/content-store.ts`, migration 8 with the central known-schema inventory and the guarded whole-batch rebuild path, the common physical-content event family, the generalized operational seams (drain, garbage collection, Vault move and verify, doctor census, Git pathspec and attributes, backup writable setup), and the snapshot writer's turn to format 3. ## 2. Shared content store design

The core port keeps one backend-agnostic application boundary: `write` accepts a body the surface already classified — exact fatally-decoded text with a preserved byte-order mark, or binary-classified bytes — and owns routing under the fixed 65,536-UTF-8-byte threshold, so no caller selects inline versus Vault. Inline INSERTs bind UTF-8 buffers through SQLite `CAST(? AS TEXT)` so the pinned Bun engine preserves a leading BOM while retaining TEXT storage, empty strings and null distinctions. A spawned native Bun regression checks exact SQLite bytes, size/hash, reopened reads, composition rollback and file-backed nulls alongside the usual Node-backed integration runner. Internal primitives remain for domain composition: a streaming bounded `stage`, a single-transaction `writeFile` that commits the record and its activation intent together behind the vault-move fence, a `writeInline` that creates no file and no physical event, and in-transaction `insertContentRecord`/`insertCommonIntent` that throw so a caller's transaction aborts. The generic record validation accepts managed keys in both the existing `artifacts/` subtree and the new `content/` subtree, while the common owner triple and `CONTENT_*` events stay exactly `memo` and `channel`.

File-backed writes follow the existing durability order: stage outside the transaction with size and SHA-256 in the same pass, one `BEGIN IMMEDIATE` transaction for record and intent, activate by rename with parent-directory fsync and a read-only mode, then one shared completion transaction that marks materialization, clears the intent, and appends `CONTENT_ACTIVATED` or `CONTENT_UNLINKED`. A failed assessment retains the intent, increments attempts, and appends `CONTENT_INTEGRITY_FAILED` with the closed metadata of security section 10.1; the ordinary completion and the start-up drain call the same helper, and an inside-transaction recheck keeps a competing drain from emitting a duplicate success. A both-present destination conflict retains both files and the intent; a source-absent retry completes only after the recorded destination's size and hash verify. Reads validate the stored representation, size, and SHA-256 against the exact returned bytes, including inline text. File reads verify the size before allocation and read a bounded buffer through one handle. They return `CONTENT_MATERIALIZING` for unmaterialized file-backed records and `CONTENT_CORRUPTED` for missing or mismatched bytes, never a synthesized success.

Managed filesystem operations resolve the selected Vault alias to its real directory, then reject symlinks and special entries in every managed parent and leaf. Memo and Channel staging derive their relative keys from that same physical root, while configuration and captured bindings retain the selected path notation for coherence checks. Handoff staging keeps its established caller-visible path under the selected root. A selected directory alias or an alias in an ancestor must preserve file-backed creation, exact reads and replay across all three domains; a root that disappears or becomes a non-directory during staging returns a typed error before domain commit. Reads inspect a regular-file descriptor opened without following links and verify its identity before consuming bytes; dangling links are unsafe entries, not absence. Activation, retry verification and unlink share the same boundary, so an unsafe path retains its intent and reports `unsafe_path` without accessing an external target. These checks protect stable managed trees; they do not provide atomic isolation from an adversarial process running as the same OS user.

Reference-aware cleanup is the only deleter of records, and its provider split is load-bearing: record ids protect rows, inline and file-backed alike, while storage keys protect the physical files an unexpired retained response may still resolve. A receipt that embeds an inline body string references no record and protects nothing, even if its body happens to equal a managed storage key. Schema 8 has no production domain or receipt format naming content records, so its default providers return no references; the adoption Tasks own their actual record-reference codecs. Integration tests inject a scoped record-ID provider over retained receipt rows to check protection and expiry without inventing that production format. Cleanup runs inside the writer transaction with the reference providers read there and preserves records whose activation intents remain pending until those intents clear; an inline row is deleted outright with no file, intent, or event, while a file-backed row's `unlink` intent — carrying the owner triple verified against the record's managed key — is committed before the record row disappears.

The derived inline fetch cache lives at `<state>/fetch-cache/<sha256>` inside the existing `state` tree: created owner-only and lazily, written read-only and fsynced before its path returns, reused per checksum, swept through `gc.graceHours`, and never trusted — a corrupted regular entry is replaced. A linked state root, cache directory or cache entry is refused, and sweeping skips unsafe entries without following them.

## 3. Migration 8, inventory, and the guarded rebuild path

Migration 8 (`shared-content-v1`) is additive DDL only: the immutable `content_records` table with table-level XOR, nonempty-key, size, digest, and inline-materialized CHECK constraints, a deliberately nonunique `sha256` index, and the `pending_fs_ops` owner columns whose all-null versus all-present triple is application validation because SQLite cannot add a multi-column table CHECK by `ALTER TABLE` and rebuilding the intent log is out of scope. Legacy `artifact_id` semantics are unchanged.

History admission precedes operational writable opening (SHR-009). The shared `sqlite/history-inspection.ts` first reads through a genuine native readonly connection with a connection-local busy timeout. Bun cannot read a cold WAL database whose sidecars are absent, so only its observed `SQLITE_CANTOPEN` failure selects a coherent private-copy inspection: the main file and any WAL are captured with bounded retries, source identity/inventory/content fingerprints are checked before and after copying, and captured bytes must match those fingerprints. Hashing uses bounded buffers; only the owned copy is opened writable for SQLite recovery, without migration or operational settings. Every owned reader, statement and scratch directory is disposed before proceeding. Other read failures, uncertain closure, unstable captures and cleanup failures stop without a writable source retry. Only confirmed file absence skips inspection; an empty history requires a successful read. The original source's main and committed WAL bytes survive unsupported/integrity refusal, including true orphan WAL. Reader-side SHM housekeeping is not claimed invariant. The ordinary migration transaction still rechecks history under `BEGIN IMMEDIATE`, and its DDL and rebuild/FK discipline remain unchanged.

The shared admission scans the full applied maximum before duplicate classification, so a future-plus-duplicate history refuses as `STORAGE_SCHEMA_UNSUPPORTED`. Doctor uses the same inspection eagerly before probes: a confirmed future error reaches the existing CLI renderer or the narrow HTTP diagnostics classifier as exit 78 or HTTP 422; a supported maximum with malformed known history remains a blocking `db.migrations` finding while other diagnostics continue. Unreadable or uncertain history produces honest database-unavailable findings with existing severity limits, including binding and backup helpers, while independent checks continue. Before-init catalog behavior is preserved. The test alias translates Bun's `readonly` to Node's `readOnly`, but actual Bun regressions cover cold, active and orphan WAL because the drivers differ when sidecars are absent.

Cold-WAL inspection needs temporary space for the database and its WAL and performs bounded-memory copies and content hashing; it is not free. A native Bun 1.4.2 check over the existing 10,000-Handoff metadata seed (10,760,192 database bytes) measured a five-sample median of 33.7 ms for admission, operational opening, a count query and logical close on the local macOS development host. Each sample uses a separate Bun process and a SQLite-checkpointed, closed fixture with no sidecars; module startup, fixture checkpointing, process shutdown and an operating-system cold-cache guarantee are outside that measurement. The permanent regression retains the existing 500 ms metadata budget. Domain adoption and assembled qualification must recheck representative data sizes; this metadata result does not establish the cost of a database packed with large inline bodies.

The central ordered known-schema inventory in `packages/core/src/known-schemas.ts` is the one knowledge source for migrator admission, preflight classification, doctor's expected maximum, and send-replay's floor: per-surface eligibility keeps send replay from version 4 on, Memo surfaces from version 7 on, and Channel surfaces nonexistent before the TASK-109 migration. Every invocation admits the applied history before any DDL: an unknown forward version refuses with `STORAGE_SCHEMA_UNSUPPORTED`, a hole, duplicate, or name mismatch with `STORAGE_INTEGRITY_ERROR`, both leaving `sqlite_master` and `schema_migrations` untouched; the refusal's public code survives the command-port wrappers through `asSchemaAdmission`. Operational CLI commands render the typed JSON envelope and catalog exit code, including real initialization and daemon start/serve. Plain `init` with an existing configuration remains the documented successful no-op; new initialization and `init --reconfigure` create a token only after migration admission succeeds. Directory preparation may precede admission. Daemon start preserves port-in-use priority, inspects a coherent private database copy before spawning, and keeps unknown health failures as `DAEMON_UNAVAILABLE`; the child still performs its own real admission and releases its own lock on synchronous or asynchronous startup refusal before creating a token, server, record or timer.

The guarded whole-batch rebuild path executes the entire pending batch — ordinary and rebuild-marked steps alike — on one dedicated non-operational connection inside exactly one transaction when the run's rebuild set is non-empty, test-injected at this Task and production-owned by TASK-107 and TASK-108. Foreign-key enforcement is verified on after open, disabled outside any transaction on that connection only, re-admitted inside the write lock through a history re-read, restored step-level savepoints for attribution only, gated by an empty full `PRAGMA foreign_key_check` before the one commit, and restored-and-verified then closed on every exit; a restoration failure reports committed or rolled-back work accurately plus an unusable connection, never a false rollback. The ordinary production path is byte-identical apart from the admission guards, and the legacy `run/migration.lock` file remains inspection evidence only.

## 4. Operational seams

The two existing physical GC call paths are the Vault command start sequence and backup composition; the daemon’s scheduled backup uses that same backup path. Its separate current-Artifact periodic checksum loop and 64 MiB budget remain unchanged. The start-up drain treats a common intent through the common executor and the shared completion transaction while legacy Artifact intents keep their existing execution and their `ARTIFACT_INTEGRITY_FAILED` metadata verbatim. Garbage collection's guard set gains live content keys and unexpired receipt keys, the sweep covers `content/` under the same grace and registry-authorization rules as `artifacts/`, and the fetch cache sweeps beside it. `vault verify` and `doctor` gain the `content.checksums` census — inline records verified by recomputing the digest over their stored text, file-backed records at their managed keys — and Vault move relocates `artifacts/` and `content/` through one root-relative copy, verify, and activate sequence with the existing owned-scratch target checks extended to `content/`. The Git pathspec set gains `content` (six entries), the `.gitattributes` contract carries five required lines with the raw snapshot-content exception ordered after the general snapshots rule, assertion surfaces idempotently reassert exact managed rules after other root rules while retaining non-managed lines in order, preserve already-correct files byte-identically, and replace changed policy files through a synced atomic rename, and the backup run's writable setup prepares the empty `content/` directory in-run without a sentinel while verify, dry-run, and preflight leave an absent directory absent. `gitBackup.largeArtifactWarningBytes` extends to shared content as the write-outcome disclosure seam; no CLI surface consumes it until the adoption Tasks land.

Physical garbage collection checks the `staging/`, `artifacts/` and `content/` roots and nested entries without following links, skips unsafe trees, and counts only actual regular-file removals. Both content censuses hash through guarded descriptors for either supported managed key family. Vault move validates source and target managed trees before writing its scratch marker or clearing owned scratch content, then applies the same checks during copy, checksum and activation. Initial Vault setup and backup writable setup also refuse an unsafe `content/` directory.

TASK-107 must apply this boundary to the legacy `ArtifactStore` stage, activation, removal and checksum paths and the legacy `executeIntent` physical executor while adopting shared content. Their existing raw physical-path handling remains outside TASK-106's common executor: a linked legacy managed parent can still resolve outside the selected Vault. TASK-107 must prove rejection with external canaries for those paths before its acceptance; the guarded shared collector and all new TASK-106 consumers are covered here.

The legacy completion-event boundary of security section 10 is part of this delivery: the drain transaction that clears a legacy intent appends its `ARTIFACT_ACTIVATED` or `ARTIFACT_UNLINKED` success event in the same transaction, exactly once, gated on that transaction's own row clear, with the association and digest taken only from an authoritative Artifact row read inside the transaction — when the row is gone the association stays null and the unavailable digest is omitted, never derived from a pathname. An in-transaction recheck keeps a stale completion from appending a false failure or bumping attempts after a competing drain won, and the ordinary `completeActivations`, `completeUnlinks`, and `completeUnlink` paths gate their appends and their `completed` counts the same way, so a late ordinary completion racing the start-up drain cannot double-append; the Vault-move owner's drain wires the real ledger and is a first-class completion path. The known association asymmetry stands disclosed: a drain-appended unlink normally carries a null Handoff association because the domain transaction already deleted the authoritative row, while the ordinary path's unlink carries the domain association; the event shape allows the nullable association and no invented lookup exists.

A both-present activation classification is a claim about two managed observations taken in two separate calls, and a competing executor of the same intent can rename the staged source into the destination between them: the files never physically coexist, so both the legacy and the common executor refresh the staged source through the same managed validation before reporting a conflict. A still-present source keeps the genuine both-present failure with both files untouched. A consumed source falls through to the existing destination-present completion — the legacy executor from a fresh destination observation, so a competitor that already settled and let its released causal unlink retire the key meets the ordinary both-gone assessment under the completion transaction's already-cleared guard, and the common executor through the recorded size-and-hash verified retry. Deterministic forced-interleaving regressions in fresh native processes schedule that rename between the real observations for both executors, and a deep control drives its competitor through the authentic drain; the real two-process contention regression keeps its original strength. The managed unsafe-path, genuine I/O, fsync, no-overwrite, and exactly-once completion rules are unchanged.

## 5. Artifact identity under ADR-0031

Every new Artifact, revisions included, takes its identity from the existing UUID generator, exactly as new sends already do; the retired `a`-plus-eight-lowercase-hex revise producer is gone while its SHA-1-named intent ids and metadata shapes stay verbatim. The format-3 reader accepts a canonical UUID or exactly the legacy short form in precisely two fields — the Artifact record's `id` and its Handoff's `currentArtifactId` — after a string guard and an explicit length predicate, so arrays, numbers, booleans, objects whatever their `toString`, upper-case hex, wrong lengths, and embedded line terminators fail as typed integrity errors without throwing. Every other UUID-typed field stays a strict UUID, workspace and User-identity strings keep their text rules, and existing identifiers, references, storage keys, file bytes, receipts, and pending intents are never rewritten. The frozen legacy qualification builds a real schema-7 installation through the genuine migration prefix with the genuine legacy producer algorithm, truthful historical actors, the real request-hash rule for the retained send receipt, and the single genuine crash leftover — an executed unlink whose completion transaction never landed — then proves the migration-8 upgrade preserves domain rows, the receipt string, pending legacy columns with null owner columns, and file bytes, that export, verify, and dry-run read the operational rows without mutating them, that restore rebuilds exact domain identity and body bytes while excluding operational rows, and that the normal drain completes the leftover with one authoritative success event.

## 6. Snapshot format 3 (representation)

The writer produces one coherent global format-3 snapshot: the format-2 families with Handoff Artifact records carrying an explicit `inlineBody: null` beside their unchanged `storageKey`, Memo shards carrying `bodyContent: { inline }` in place of `body`, a manifest whose Channel count is zero and whose `contentDigests` map is empty, and no `channels/` or `content/` snapshot files. File-backed Artifact bytes keep arriving through the committed `artifacts/` tree outside `contentDigests`, which never covers Handoff Artifact files at any M9 build. Format-3 Handoff shards parse through the duplicate-key-rejecting parser over the same safe bounded reader the Memo shards use; formats 1 and 2 keep their existing parsers and rules. Project metadata also rejects duplicate keys and noncanonical bytes. Format 3 preserves stored Project slug strings, including Unicode case-fold expansions produced by the existing CLI. It rejects embedded NUL before import because SQLite NOCASE comparison can ignore text after NUL; it does not reapply input-only slug grammar or normalize stored values. Format 3 rejects duplicate Project slugs before import using SQLite's ASCII `NOCASE` comparison: `alpha` and `ALPHA` collide, while `Ä` and `ä` remain distinct and retain their original spelling. Formats 1 and 2 keep their frozen behavior. Existing Project/Binding UUIDs, known field types, arrays and enums are checked before use, without adding an unknown-field whitelist, a local path-existence requirement or a current-Installation identity requirement to historical Bindings; those Bindings remain excluded from restore.

The reader accepts formats 1, 2, and 3 with frozen per-format event families decoupled from the runtime union: format 1 carries the pre-M7 family, format 2 adds the Memo family, format 3 adds the common physical-content family with its fixed system/null header and closed metadata validated as historical attribution only — no live owner, record, or file lookup, and `ownerDomain: "channel"` valid before Channel tables exist. A recognized later representation fails closed with `VAULT_SCHEMA_UNSUPPORTED` (HTTP 409, CLI 78) before import: an inline Artifact body, a Vault-backed Memo body, a nonempty `contentDigests` map, nonempty Channel structure, or a recognized Channel domain event name including ledger-only input. Unknown event names and events outside a format’s frozen family fail as integrity errors before import. Malformed records of supported families remain integrity failures, an `inlineBody` field inside a format-1/2 Artifact is an integrity failure, and restore never manufactures receipts.

## 9. Handoff adoption at schema 9

The Handoff migration normalizes Artifact bodies into immutable content records and makes `artifacts.content_record_id` the private reference. It rebuilds the complete foreign-key component (`artifacts`, `handoffs`, `review_notes`, `deletion_requests`, and `events`) through the dedicated whole-batch runner described in section 3. Foreign-key enforcement is disabled outside the transaction on that non-operational connection only, the complete pending batch commits atomically after a full foreign-key check, and enforcement is restored and verified before the connection closes. Migration 8 remains the additive foundation. Migration 9 assigns fresh private content UUIDs without changing Handoff or Artifact identities, including legacy short Artifact ids, storage keys, file bytes, materialization flags, associations, raw receipt strings, pending operations, indexes or triggers. It does not repack historical small files.

New sends, fan-out copies and revisions route through `packages/core/src/content.ts` and `packages/adapters/src/content-store.ts`. Each Artifact owns an independent content record. Accepted text of at most 65,536 UTF-8 bytes is inline; larger text and binary-classified inputs remain files. Classification uses the logical original filename and MIME policy rather than an upload spool name. Invalid UTF-8 file input follows the binary policy, while invalid surrogate input to the text producer is rejected before hashing or persistence. The native Bun regression retains the exact leading BOM, CRLF and final-newline state through UTF-8 buffer binding and SQLite `CAST(? AS TEXT)`; a JavaScript string binding is not equivalent on the pinned engine.

### Public and internal contracts

The Handoff data-DTO revision is **breaking**: every affected `storageKey` remains present and becomes `string | null`, with null for inline content. CLI, HTTP, Web consumers, examples and contract goldens follow [interface section 38.8](../specs/interfaces-and-operations.md#388-public-contract-classification-and-format-3-serialization). The response envelope, protocol version 1 and `/api/v1` prefix remain unchanged under ADR-0030; this is not a blanket compatibility claim. Core body ports and adapter constructors also gain required storage-neutral dependencies, so internal TypeScript callers must update. Content-record UUIDs remain private and are not added to public Artifact summaries.

The selected Handoff read checks that its current Artifact belongs to that Handoff before projecting body metadata. Missing rows, wrong ownership and missing records retain a private integrity marker rather than becoming a legitimate null Artifact. Existing actor, Note, Revision and Row Version guards, filtering and page selection retain their priority before a selected corrupt body is reported. Accept, revise, no-change resolution and deletion verify current authority and required body bytes before claiming success. Doctor, Vault verification and backup also detect broken live links. Record removal requires the reference proof in the same writer transaction as retirement; an unavailable proof prevents physical garbage collection and fetch-cache sweeping.

### Serving and operational safety

`packages/adapters/src/artifact-body-ports.ts` adapts Handoff body reads to the shared record without exposing its backend to domain consumers. Inline bodies always validate their stored byte size and SHA-256. `fetch.localPath` is a real readable Vault file or a derived read-only inline cache entry; editing requires copying it to a workspace. Cache absence does not make an inline body unmaterialized, and cache files never become authoritative or enter backups.

File transport uses the actual extent of the same guarded descriptor it serves, preserving full-body, Range, suffix and 416 behavior when a file changes size before acquisition. Public recorded size, SHA-256 and ETag stay recorded metadata. Strict integrity checks still require that recorded size and digest; descriptor failures close the acquired resource without masking the original error. First-fetch writes check the known run-directory move fence before SQL and the database move fence inside the transaction, including warm factories with shared database dependencies. Eligible CLI fetches and admitted recipient/User HTTP 200 or 206 reads record the first fetch exactly once without incrementing Row Version; sender reads, repeats, reveal-only reads and fresh 416 refusals do not. Missing or private content cannot bypass the original actor boundary.

Legacy file operations now share guarded managed-path handling, durable parent-directory synchronization and causal settlement across ordinary completion and restart drain. Settlement rechecks authoritative intent/key/Artifact associations and lets only the winning transaction append success. Deferred unlink cannot outrun an unsettled activation for its key. Failed ownership or reference proofs retain the evidence and prevent unsafe cleanup rather than synthesizing successful materialization or deletion.

When current-body verification fails during a revision, the command rechecks the captured Handoff Row Version once. A changed version returns `ROW_VERSION_CONFLICT`; unchanged authority preserves the original integrity refusal. This failure check neither retries the operation nor replaces its final SQL compare-and-set, and body I/O stays outside the transaction.

### Backup and retained verification

Format-3 Handoff Artifact records carry the closed pair `storageKey: string | null` and `inlineBody: string | null`, with exactly one non-null arm; this is not the Memo/Channel `BodyContent` union. Inline text is validated against its recorded UTF-8 size, digest and threshold. Handoff files retain their `artifacts/` paths outside `contentDigests`. Export, verification, dry-run and restore preserve BOM, CRLF and final-newline state. Restore assigns fresh private content UUIDs while preserving Handoff/Artifact identities and ledger associations, and excludes receipts and derived cache files. Formats 1 and 2 keep their frozen readers. Vault-backed Memo bodies and Channel structures remain later-generation representations until their owning adoption Tasks; coherent unsupported inventory fails before import.

Vault physical file counts and the content-record census measure different things.
