## Scope and owners

TASK-114 is a Standard Task under EPIC-017. It qualifies the T1 concurrency risk for the Channel write path under SHR-015 and CHN-012, using the AJ-28 compiled surface and the shared v0.1.3 release candidate. The note explains the load, the evidence and the retry-policy decision; it does not accept the Task, install the product, publish the release or approve a consumer.

The Writer owns the harness, the permanent compiled regression and the qualification runner. The Supervisor owns the frozen candidate, the isolated 6 x 8 matrices, the raw evidence and the final `make test`; the independent Reviewer confirms the evidence and the policy change. The event-driven tail submitter is the one harness correction accepted before the official matrices: it keeps the strict handle/submit overlap rule and makes the overlap hold by construction.

## Load model

The permanent case runs two iterations of five initial compiled submitters on one Channel, plus one event-driven tail submitter. The qualification case runs six runs of eight initial submitters and the same tail. Both use one main participant, the worker-a and worker-b participants, and in qualification the worker-c worker and judge-a judge; every body is deterministic and unique per run, with independently computed size and SHA-256. The bodies exercise inline content at 65,536 bytes, inline content below it, file-backed content at 65,537 bytes and above, a 4 KiB relay request, a 1 MiB file-backed report, a 2 MiB file-backed report, an 8 KiB judge question, and a 128 KiB file-backed report. Assignments cover an open assignment, a closed assignment whose message must record `assignmentLate: true`, and no assignment; contexts and the relay target are fixed per slot.

Every product process is the compiled `dist/sorage` with a temporary `SORAGE_HOME`; no test reads the developer's real home. Every measured submit, wait, handle, replay-only and identical-replay command runs through the test-only start-gate wrapper, which records its own PID, spawn instant and the instant immediately before `exec`, and every process's exit is recorded with its status and envelope under the same child timeout. The initial submitters share one readiness file and one release gate; the wait and handle commands use an always-present gate; the tail submitter has its own absent gate, which the handler driver opens immediately before it spawns its first duplicate-pair handle attempt. The test records each process's spawn, exec and exit instants, so the tail is active while that handle executes and the strict handle/submit interval rule holds.

The Coordinator is one or more fresh compiled waits against the exact unfiltered dossier command, with a 20-second timeout and a 1-second poll interval. The first wait starts before the release gate, is confirmed alive after a 2,000 ms polling window, and is re-invoked after every return until the submit load has settled and every expected worker-a message has been observed or the Coordinator window ends. A return that adds no new message ID is followed by the next wait after 1,000 ms, the product poll interval, so a Coordinator that sees an already-returned unhandled message does not create a restart storm; a return that adds a new ID restarts immediately. This is the one deliberate pacing difference from the plan's "immediately starts another wait" and it affects only continuity timing, not the deadline or return rules. The handler driver starts before the gate, polls committed rows, handles only non-worker-a senders, starts the duplicate pair on the first non-worker-a message, keeps at most two handles in flight, and never handles a worker-a message, so the tail and the other worker-a messages remain available to the waits.

## Independent reconciliation

The test never treats a submit response or the product's list path as the authority. After all children exit it reads the installation's SQLite database directly: `channel_messages`, `content_records`, `events`, `idempotency_keys`, and `pending_fs_ops`. It resolves every file-backed `storage_key` under the test Vault, reads the exact bytes and recomputes SHA-256. It requires one message, one submission event, one retained receipt and one content record per logical slot; the receipt scope must be exactly `channel-submit:<installationId>:<channelId>`; and the stored sender, handle, kind, assignment, `assignmentLate`, relay target, all three context fields, body size and digest must match the accepted input.

Every first submit response, identical retry response, replay-only response and identical-replay response is compared as a complete summary against the immutable row and the retained receipt summary, including the submit-time version 1 and unhandled state. Handle responses are compared with the recorded decision and version 2, and a recorded decision is attributed to the single exit-0 attempt that reported it; a nonzero process outside the deliberate duplicate pair must leave the message unhandled at version 1 with no handling event. The duplicate-pair loser's `ROW_VERSION_CONFLICT` details and every superseded attempt's post-refusal decision and event metadata are compared with the stored decision and its `CHANNEL_MESSAGE_HANDLED` event. Refusals are a closed set: only a typed `STORAGE_INSPECTION_UNAVAILABLE` with `storageContention: true`, the same code without that detail and with the exact pinned coherence-exhaustion message, or the deliberate duplicate pair's expected `ROW_VERSION_CONFLICT` pass. A permitted refusal must be exactly exit 75 with no signal and a valid typed envelope; every other code, exit, signal or untyped output fails.

`contentActivating: false` requires a materialized record and exact bytes; `true` is accepted for a record that later materialized and for an unconfirmed probe, and true is never accepted for inline content. `bodyPreviewUnavailable` is checked against the stored decision, and the public paginated `channel messages --all` listing plus `channel read` must agree with the direct database and Vault reads. Waits are snapshot-checked around their loop to prove they never change a worker-a message, its events or its receipt.

## Retry policy and decision

Before this Task the Channel coherence loop allowed three write attempts and, after an `external-commit` mismatch, retried immediately with no sleep; a busy `BEGIN IMMEDIATE` was already the separate typed contention refusal. The list budget and the 5,000 ms SQLite busy timeout are unchanged. The qualification classifies observable refusals by the closed set above; a failure to establish a coherent transaction is the exact pinned `STORAGE_INSPECTION_UNAVAILABLE` message with no contention detail. Internal successful retries remain invisible, so the matrix reports observable exhaustion and client retries rather than claiming a count of every internal retry.

The isolated pre-change 6 x 8 matrix on candidate `39e39159f6e518b7` recorded six valid passing runs and 19 coherence-budget exhaustions (5, 6, 2, 3, 3, 0 per run), with 0 contention refusals, 6 expected duplicate-pair row-version conflicts and 19 converging client retries. That triggered the conditional backoff. The decision keeps `CHANNEL_WRITE_ATTEMPTS = 3` and adds a delay only after an `external-commit` mismatch and only before another attempt: `delay = floor(random() * min(200, 100 * 2^retryIndex))` milliseconds, with `retryIndex` 0 for the first retry and 1 for the second. The first attempt, a success, a `vault-path-changed` retry, a `SERVICE_PAUSED` fence, a non-coherence failure and the final exhausted attempt never delay. The delay is outside every transaction, and every attempt still checks the fence, captures the external version, reads a fresh binding, and restages the accepted body when the binding path changed. The accepted input, request hash and idempotency key are reused.

The random source and sleep are injected through the `ChannelBackoffPorts` seam; the adapter composes `blockingSleepMs` and `Math.random`, and tests inject a deterministic random sequence and a recording sleep. The base is 100 ms from the pre-change commit-spacing proxy: the distinct domain-event instants gave a median gap of 91 ms and a p95 of 939 ms, but those gaps include client-retry and handle-wave idle time, so this is a commit-spacing proxy, not a measured transaction duration. Deterministic unit tests cover two external-commit mismatches followed by success with exact jittered delays and the same input, hash and key; three mismatches producing the pinned exhaustion envelope after exactly two sleeps; a non-coherence failure with no delay; a `vault-path-changed` exhaustion with no delay and `CONFIG_CONFLICT`; and a binding change during retry that restages into the new binding with unchanged input, hash and key.

The earlier post-change 6 x 8 matrix on the backoff code candidate `b2399315c6b704c3` recorded six valid passing runs and 4 coherence-budget exhaustions (2, 1, 0, 0, 1, 0 per run), with 0 contention refusals, 6 expected duplicate-pair row-version conflicts and 4 converging client retries, and no loss, duplicate or misattribution; those counts were verified from the raw records. That matrix used harness revision 1 and is superseded by the corrected-harness rerun of the same binary, candidate `da337e1e854e9a6c`, which recorded six valid passing runs and 2 coherence-budget exhaustions (0, 0, 0, 1, 0, 1 per run) with 0 contention refusals, 6 expected duplicate-pair row-version conflicts and 2 converging client retries, and no loss, duplicate or misattribution. The retry timing change is non-breaking and behavior-preserving under [interface section 38.10](../specs/interfaces-and-operations.md#3810-epic-017-public-contract-classification); it introduces no error code, exit category, DTO, golden, schema, receipt, event or Vault-layout change, and its migration impact is none.

## Permanent regression versus qualification

The permanent compiled case runs inside `make test-e2e` and therefore inside `make test`: `bun run test:e2e -- test/e2e/channel-concurrency-qualification.e2e.test.ts` executes two iterations of five initial submitters plus the tail, a 150-second test timeout, a 45-second child timeout, a 60-second per-run hard bound, and full child and connection cleanup. Every correctness assertion is hard; the overlap rule is hard for at least two concurrently executing initial submitters, and the full overlap and witness metrics are recorded for review. The case is regression evidence only and never triggers backoff.

The qualification case is skipped unless `SORAGE_CHANNEL_QUALIFICATION=1` is set, so `make test` never inherits its runtime. It runs six isolated 6 x 8 runs with the same tail, a 480-second test timeout and the same 60-second per-run bound. The Supervisor command is `SORAGE_CHANNEL_QUALIFICATION=1 SORAGE_QUALIFICATION_EVIDENCE=<evidence-directory> bun run test:e2e -- test/e2e/channel-concurrency-qualification.e2e.test.ts`; the case must run alone, not concurrently with `make test`, `make package` or another qualification run.

A run is `pass` only when the all-N initial submit overlap, the handle/submit overlap, the wait/commit overlap and the another-message witness hold, every refusal is in the closed set, every retry is bounded (at most two identical client retries after 500 ms and 1,000 ms), no message is lost, duplicated or misattributed, and every response, receipt, event, content record, Vault byte, wait and public read agrees. A missing validity condition makes the run `invalid`, never a pass; a correctness failure makes it `fail`. The qualification case writes `run-01.json` through `run-06.json` and `summary.json` to the supplied evidence directory and exits nonzero after writing them if any run is not a pass. Raw evidence stays outside the repository; the tracked note reports aggregates only.

## Limits

The evidence covers one macOS host with SQLite WAL. It does not qualify OS crashes, power loss, or a real Aquarium or Herdr consumer, and it does not claim that every internal successful retry was counted. The contention witness is a direct count of other messages committed inside submit windows plus a supporting `PRAGMA data_version` sampler, not a proof of every transaction overlap. A timed-out wait uses a 250 ms visibility margin after `created_at`, so a commit that lands just after the deadline is not treated as visible, and it accepts handling only when `handled_at` precedes that wait's start. The 100 ms base is a commit-spacing proxy, not measured transaction duration. The permanent 2 x 5 case is regression evidence, not a backoff trigger, and zero exhaustion in a later run is an internal target rather than a guarantee. Raw run evidence, process identities and run paths remain outside the repository.
