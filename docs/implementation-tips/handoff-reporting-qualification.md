# Handoff reporting qualification

This map describes implementation and reproducible checks; the [roadmap](../roadmap/README.md#epic-019-handoff-processing-status-and-recipient-comment) alone records delivery state.

## Core and CLI boundary

`packages/core/src/reporting-commands.ts` owns recipient/User-proxy comment and processing admission, positive safe-integer observations, Revision-before-Row-Version conflicts, current evidence and metadata-only report events. `review-commands.ts` maps legacy review set to the same replacement and comment event, retains text on withdrawal, and removes any non-terminal current comment only for confirmed User administration. The SQLite review store commits the compare-and-set, comment, processing, first engagement and all events together. One logical replacement plus processing transition increments Row Version once.

The CLI exposes `comment show`, `comment set`, `processing start` and `processing complete`. Metadata and comment reads share the covered read-only storage path. Human get/list output shows reading and processing separately from review, labels older comment targets and presents declined/withdrawn work as stopped. HTTP and MCP reporting resources use the same application guards. Existing HTTP/Web/MCP writers carry the mandatory legacy observations; the daemon-served Web also exposes the reporting controls described below.

Fresh `review set` needs target Revision and Row Version; review withdraw/remove, revise/no-change and deletion approval need Row Version. Never manufacture an observation from a loaded Handoff in production. Receipt-bearing revise and deletion approval validate supplied scalars and source material, retain their original request hashes and keys, replay a matching successful historical outcome unchanged, and only then require fresh observations on a receipt miss. Old successful outcomes are not expanded into current DTOs. A retry must retain the original request, including observations; a conflict requires a new explicit decision about the retained proposal.

## Reading, retention and Project protection

New sends initialize unconfirmed reading and not-started processing. Changed content increments Revision, clears current read/start/completion evidence and retains the comment with its original target and inactive request state. No-change and withdrawal preserve the evidence. General comments do not block acceptance; acceptance never implies processing completion, and accepted work can start or complete. Decline deactivates an active request without changing its purpose, author, target or body, preserves recorded processing and prevents further processing. A later general explanation preserves that stopped review outcome. Tombstones expose no current comment or reporting evidence.

Successful recipient/User body delivery settles the acquired Artifact and Revision against the live Handoff inside the short fenced transaction. It records the first current-Revision receipt/event without changing Row Version, and preserves the separate historical first-fetch marker. A stale acquisition cannot overwrite a newer receipt or falsely read the new Revision. Successful delivery of an older acquired body still records the independent historical first-fetch marker/event exactly once, preventing sender withdrawal even when the new Revision remains unconfirmed. The identity mismatch skips only the current-Revision receipt; deleted Handoffs still settle neither record. Metadata reads, sender delivery, failed/cancelled delivery and already-settled current reads create no receipt. Comment removal cannot clear permanent engagement or restore sender withdrawal.

HTTP body preparation separates its pre-stream historical first-fetch admission from current-Revision delivery settlement. The historical marker and existing Vault-move fences still run before any body bytes, preserving withdrawal protection even if an admitted transfer later fails. The current receipt waits for the response's actual `finish` event after bounded streaming from the same acquired handle; queued writes or an `end()` call alone do not establish delivery. Read errors, zero progress, truncation, client cancellation and premature response closure create no current receipt/event. Descriptor cleanup failure is an independent diagnostic: after a proven finish the route still settles the successfully delivered identity and warns, while cleanup failure cannot turn an incomplete body into a successful delivery. Range admission and already-closed responses remain ahead of historical settlement. Local-path CLI fetch retains its combined acquisition/settlement behavior.

A late current-receipt failure after completed delivery emits the existing daemon completion warning; the transport never fabricates a receipt, rewrites a completed body response or retries the mutation. An unexpected post-settlement error does not claim a committed or rolled-back outcome it did not observe. The captured Artifact and Revision still fence successful settlement, so an older delivered body cannot mark a new Revision read or overwrite a newer receipt. No transaction spans streaming or another await.

Project unbind counts the union of non-deleted open review work and accepted known not-started/in-progress work, including archive and the last binding. Each Handoff counts once. Completed or accepted legacy-unrecorded work adds no invented pending contribution; approved deletion removes the live contribution. Review next actor stays review-specific.

## Daemon-served Web reporting

The inbox and outbox show current-Revision reading, processing and body-free comment attribution. Accepted not-started/in-progress work remains unfinished even when its review next actor is null; completed and legacy-unrecorded work have distinct labels. Declined and withdrawn work is shown as stopped before displaying historical processing evidence. Detail displays the evidence Revision and timestamps alongside review state, then reads the one retained comment through the separate comment endpoint. Its purpose, activity, author and target Revision remain visible, including an older-Revision label; a separately acquired comment targeting a newer Revision is explicitly labeled newer than this view without refreshing its proposal; received bodies use text nodes rather than executable HTML.

Recipient reporting explicitly acts as the existing User proxy. Set comment selects general explanation or an explicit change request; terminal states permit general reports only. Start and complete may include the exact draft as an atomic general replacement when the checkbox is selected; leaving it clear retains the existing comment. Start without replacement may coexist with an active request, while general replacement and completion are disabled until that request is resolved or withdrawn. Acceptance remains separate from processing, accepted and archived reporting stays available, declined/withdrawn processing cannot restart, and tombstones expose no report or revision controls. The existing explicit change-request controls retain their HTTP route and User provenance; Withdraw request ends activity without deleting retained text.

The forms keep their original Revision and Row Version until a successful mutation or explicit new inspection. A typed refusal leaves the entire form connected, including exact draft text, selected purpose, optional-replacement checkbox, selected revision file and deletion confirmation. Network failure states that the outcome is unknown, retains the proposal and observations, and performs no automatic refresh or retry. An explicit page reload is inspection that discards the old form; the user must reconcile its retained proposal before a new submission. Successful preview is body acquisition and can settle reading, while the metadata card deliberately retains its original observation until explicit inspection; comment and metadata reads never imply body delivery.

`test/e2e/handoff-reporting-web.e2e.test.ts` drives the compiled executable, real daemon/SQLite and Chromium at desktop 1280×900 and mobile 390×844. It covers general feedback through acceptance, optional start/completion replacements, direct completion without replacement, sender-side outbox discovery, accepted pending/in-progress/completed/unrecorded evidence, archived terminal updates, active-request guards and decline-to-inactive-request-to-general reporting without restart, changed-content upload with older comment attribution, tombstone controls, safe rendering and named controls. Same-Revision and changed-Revision conflicts verify unchanged requested domain rows/events, exact original observations and the complete retained proposal; a deliberately interrupted request verifies honest unknown-outcome handling. A held comment GET raced against real revise/comment writes verifies newer-than-view attribution without a proposal refresh. The fixture records identity, DOM, screenshots, console diagnostics and an axe pass of the reporting detail at both viewports. Its legacy-unrecorded input is an explicit fixture, not a migration drill; its interrupted request proves client uncertainty behavior, not every possible server-commit/disconnect schedule. The existing AJ-12 legacy note conflict, AJ-13 administration, compose, Project, backup and accessibility journeys remain regressions. The administration fixture selects the named legacy Review note field and waits for the separately loaded comment body, so adding a general-report draft does not redirect its intended change-request step. Browser plugin not available; this uses the repository's existing Playwright Chromium workflow without installing dependencies.

This Web candidate changes internal assets, visible presentation and client requests to existing authenticated HTTP use cases. It adds no DTO, error, protocol, configuration, schema, backup generation or migration, and changes no existing golden contract. The public behavior is the adopted section-40 reporting flow; prior transport/storage compatibility classifications remain unchanged. Independent review and assembled AJ-33 qualification retain their owning workflow and Task boundaries.
