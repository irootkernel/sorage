# Channel adoption hardening and v0.1.3 release readiness

This is the execution dossier for [EPIC-017](../roadmap/README.md#epic-017-channel-adoption-hardening-and-v013-release-readiness). The roadmap alone records lifecycle state, ordering and eligibility. [ADR-0033](../architecture-decision-records/README.md#adr-0033-channel-adoption-hardening-and-the-shared-v013-release) records the material decision, and TASK-111 adopted its contracts into the [required specification](../specs/required-specification.md#21-agent-communication-channels-and-shared-content-storage-milestone-m9), [interface section 38](../specs/interfaces-and-operations.md#38-shared-content-and-agent-communication-channels-milestone-m9) and the other canonical owners on 2026-10-21; those adopted contracts, not this dossier, are normative, and the pre-adoption statements the record superseded are reconciled there. This dossier preserves the approved planning direction and the evidence map through delivery and is retired at Epic closeout.

## Problem and product outcome

Aquarium plans to route every Executor and Evaluator report in its Epic Squad workflow to the Coordinator through Sorage Channels, with several roles submitting concurrently from native subagents or separate CLI sessions that share one Installation. Its 2026-10-20 adoption request, reviewed against `63291a9`, found that expected storage contention and pending content activation can surface as untyped usage errors, early wait exits, or failures that hide committed outcomes. Sorage confirmed each finding against the same revision by reading the source; no command or test was executed for this registration.

On 2026-10-21 Master decided to publish M8, M9 and this Epic together as v0.1.3 once the Epic completes. Aquarium is expected to adapt its setup and consumer contracts in its v0.1.21 release and then install Sorage v0.1.3 through its global setup. The product outcome is a v0.1.3 candidate whose Channel commands return typed, retryable results under concurrent use, never report a committed outcome as a plain failure, document the storage they write, and qualify the complete M8 and M9 journeys on the exact candidate.

## Approved decisions

- **Shared release.** One v0.1.3 release on the v0.1.x line carries M8, M9 and this Epic. M9's deliberately breaking Handoff `storageKey` contract and its one-way upgrade from schema 7 through 11 therefore ship in a patch version, and the release notes and upgrade guidance must state both prominently.
- **Publication coordination.** Publication follows a verified local candidate whose checksum is shared with Aquarium for rehearsal and Aquarium's confirmation that its v0.1.21 adoption is ready. A published v0.1.x release is immediately eligible for Aquarium's global setup resolver, including older Aquarium releases that still expect the v0.1.2 `doctor` catalog.
- **Contention (D1).** Classify database open, migration and actor-resolution failures in the shared CLI and adapter layers rather than per Channel action. Expected contention returns the JSON error envelope with a retryable code in the exit-75 category for Channel, Handoff and Project commands; TASK-111 chooses between an additive extension of an existing retryable row under [ADR-0032](../architecture-decision-records/README.md#adr-0032-memo-operational-coherence-errors-in-m9) and a new code. A Channel command resolves its actor on its existing connection.
- **Waiting (D3).** Channel waits and the Handoff `inbox --wait` loop keep polling across retryable listing failures until the deadline and report a failure only when it persists at the deadline. TASK-111 decides whether the response reports a retry count.
- **Committed outcomes (D5, D2).** A committed outcome is never reported as a plain failure. A submit whose message committed while its content is still activating returns the committed message ID and summary, and replay-only reports the same message; a committed `handle` returns its decision with an explicit unavailable-preview indication.
- **Recovery text (W1, C1).** Channel errors carry Channel-specific, state-aware recovery text, and no Channel hint suggests a fresh idempotency key for an unknown outcome.
- **Filters (C2).** Unknown participant and assignment filters return the not-found codes interface section 38.4 already requires; this corrects a defect and does not change the contract.
- **Main-directed new attempt (C1).** A new direct main-participant assignment for a new attempt is a genuinely new intent: the assigned role may submit its existing result once under a new idempotency key bound to the new `--context-attempt`. Authority comes only from the main participant through the role's own direct instruction surface; a Channel message body, recovery hint, replay result or changed context field confers none. The earlier submission's outcome stays unknown and may still commit, main treats a message bound to a superseded attempt as stale, and a role never retries on its own initiative (CHN-006).
- **Writable storage (C3).** Document the home and Vault paths every Channel command may write, including startup recovery and logging, and state that reads and waits are non-mutating for domain records only, not at the filesystem level. A non-mutating read and wait path is recorded as [future work](future-work.md#non-mutating-channel-read-and-wait-path) and is not part of this Epic.
- **Concurrency (T1).** Qualify five to eight concurrent submitting processes on one Channel with concurrent waits and handling, and add bounded backoff with jitter only if that qualification shows retry exhaustion.

Non-goals:

- Per-participant credentials; SEC-013 cooperative attribution remains the trust model.
- Automatic wake-up (CHN-010), Channel HTTP routes, and Channel Web screens.
- Oldest-first listing or a newer-than cursor.
- Schema, snapshot-format, or Vault-layout changes, unless TASK-111 justifies one through the material change process.
- Haepari VM verification adoption, which would arrive as a separate future request.
- Edits to Aquarium or another consumer repository, installation, publication, and broker operations.

## Coordinator waiting model

The Coordinator learns of Executor and Evaluator messages by polling, not by interrupt. It runs `sorage channel messages <channel> --unhandled --wait --timeout <seconds> --json`; under [interface section 38.5](../specs/interfaces-and-operations.md#385-channel-waiting) the wait returns immediately when an unhandled matching message already exists, and otherwise polls SQLite every `--interval` seconds, default 2, until an arrival or the timeout. Submitting roles only record messages: Sorage sends the Coordinator no signal and injects nothing into its prompt input, which is the separation [ADR-0030](../architecture-decision-records/README.md#adr-0030-agent-communication-channels-and-shared-content-storage-in-m9) exists to preserve. Because every wait is a fresh CLI process that runs startup recovery, this loop stays robust under concurrent submissions only after D1, D3 and T1 are resolved.

## Verification scenarios

- Forced Project-port creation failure, migration failure and a busy `BEGIN IMMEDIATE` for Channel, Handoff and Project commands return the typed envelope and retryable exit with `--json`; only genuine usage errors keep exit 2.
- A Channel command performs one open-and-migrate for its operational and actor-resolution work and leaves no connection open.
- A wait that meets `STORAGE_INSPECTION_UNAVAILABLE` or `CONTENT_MATERIALIZING` while polling keeps waiting and returns later arrivals; a failure that persists to the deadline is reported; an empty timeout still exits 0 with `meta.timedOut: true`.
- A submit with paused activation returns the committed message ID and summary, replay-only with the original key returns the same message, and no duplicate message exists.
- A `handle` whose preview fails after commit returns success with its decision and the unavailable-preview indication, and a repeated `handle` returns accurate state-specific recovery text.
- Unknown participant or assignment filters fail immediately with the not-found codes, with and without `--wait`.
- A main-directed new attempt produces exactly one new message under a new key and the new attempt context, while a late original remains distinguishable as superseded.
- Five to eight concurrent compiled submitters with a waiting Coordinator and concurrent handling lose, duplicate and misattribute nothing.
- The v0.1.2-to-candidate upgrade, restore drill and preflight transitions pass in an isolated home, and no developer Sorage home is read or written.
