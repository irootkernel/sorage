# Changelog

This file records concise shipped outcomes and the planned next stable release.

## v0.1.3 - Unreleased

### Added

- Add `sorage preflight` to inspect Installation compatibility without migration or managed-storage writes.
- Add `sorage send --replay-only` to inspect original-request receipts without sending again, preserving unknown outcomes when recovery evidence is unavailable.
- Harden the standalone shipped agent policy for explicit authority, pinned deletion, observed-version conflicts, untrusted content and recovery using original send material.
- Route newly accepted Handoff text of at most 65,536 UTF-8 bytes to SQLite, with larger text and binary content kept in the Vault. Preserve existing file-backed Artifacts and return a readable Vault or derived fetch-cache path from `fetch`.
- Store newly accepted Project Memo bodies through the shared SQLite/Vault interface: up to 65,536 UTF-8 bytes inline and larger text in immutable files, bounded by `artifact.maxBytes`. The existing Memo JSON responses and the 512 KiB JSON request limit are preserved, with multipart create/update added for larger bodies and literal search, title-only edits and the Web recovery gate retained across both storage backends; complete historical reads and original receipt output stay independent of a later lowered input cap, while newly supplied request bodies still meet the current input bounds.
- Add agent communication Channels rebuilt to Handoff- and Memo-level simplicity under [ADR-0034](docs/architecture-decision-records/README.md#adr-0034-sorage-mcp-adapter-zero-write-reads-and-the-channel-rebuild): Channels addressed by globally unique name, participants by handle and messages by per-Channel sequence number; a five-step loop of create, add, post, messages and ack; idempotent create, add, remove, ack and close; post retries safe by content with `duplicate: true`; User-actor provenance with the handle in event metadata; full-inline-body listing with `bodyPath` and `bodyPending`; pending-inclusive waiting with `--after` and a 60-second default; zero-write Channel reads; and format-3 export/restore of the rebuilt Channel records. The unreleased EPIC-016/017 Channel surface, error codes, schema 11 and format-3 Channel representation are replaced in place before first publication, so no published release or real home carries them.
- Add `sorage mcp`, a STDIO MCP server exposing 31 messaging tools for Handoffs, Memos, Channels and Project reads, each running as a `sorage --json` child process of the same executable with an optional `cwd`, returning the CLI envelope with `isError`, accurate read-only and destructive annotations on all four hints, and 30-second wait defaults; bodies are inline and file arguments are confined to the call's workspace, refused with `SOURCE_OUTSIDE_WORKSPACE` before any child process; administration stays CLI-only and the server never self-registers.
- Make the covered read commands write nothing under [RDR-001](docs/specs/required-specification.md): Handoff `inbox` (with `--wait`), `outbox`, `get`, `events` and `review show`, Memo `list` and `show`, Project `list` and `show`, and Channel `messages`, `list` and `show` keep their outputs on a migrated installation and lose their startup recovery, migration, cleanup and log writes; writers keep WAL sidecars persistent through `SQLITE_FCNTL_PERSIST_WAL`. Disclosed upgrade-window change: a read on an unmigrated older or empty database now returns `STORAGE_MIGRATION_REQUIRED` with exit 78 until `sorage backup run` (or an intended MCP write call) completes the migration, and a missing database file returns `STORAGE_INTEGRITY_ERROR` with exit 73 without creating one.
- Add `sorage revise --body <text>` so no messaging operation needs a temporary file: `revise` accepts exactly one of `--body`, `--file` and `--no-change --reason`.

### Changed

- **Breaking data contract:** Handoff `storageKey` fields are always present and may be `null` for inline content. Update string-only consumers; the response envelope, protocol version 1 and `/api/v1` prefix remain unchanged under [ADR-0030](docs/architecture-decision-records/README.md#adr-0030-agent-communication-channels-and-shared-content-storage-in-m9).
- Report committed outcomes truthfully: a committed Handoff or Channel operation is never reported as a plain failure, and the rebuilt Channel surface keeps exactly that rule — a committed post or ack returns its committed result with any post-commit failure disclosed as a warning ([CHN-012](docs/specs/required-specification.md))
- Classify storage-preparation contention in the shared CLI and adapter layers under [SHR-015](docs/specs/required-specification.md), including the write-protected installation: database open, migration, actor-resolution, keyed-lookup expiry-cleanup, startup-drain, and busy write-lock failures on Channel, Handoff, and Project operational commands return the typed `STORAGE_INSPECTION_UNAVAILABLE` envelope with HTTP 503 and exit 75 — carrying per-surface recovery guidance and asserting the invoking command committed none of the requested changes — instead of an untyped exit-2 message or `INTERNAL_ERROR` exit 1; on a write-protected installation, where a readonly database-open or migration failure was previously `INTERNAL_ERROR` exit 1 on Channel surfaces, an untyped exit-2 line on Handoff and Project surfaces, and a 500 answer on the daemon's Handoff and Project routes (now 503 there), the recovery directs restoring write access to the Sorage home and Vault (permissions, sandbox, or read-only mount) and retrying the identical command with its original mode, inputs, and idempotency key on the Handoff surfaces (the Project retry names no mode or key; the rebuilt Channel surface carries no keys), with an unknown keyed send inspected through `--replay-only` first because that inspection runs without write access; no code is added or removed, the HTTP and exit mapping of every code and the pinned count stay unchanged, and the `STORAGE_INSPECTION_UNAVAILABLE` meaning text changes. Genuine usage errors keep exit 2, an unreadable configuration on an operational command path is `CONFIG_INVALID` exit 78, replay-only inspection keeps its recovery semantics, and excluded surfaces (Memo, vault, backup, config, doctor, preflight) keep their existing contracts while the daemon's Handoff and Project routes inherit the classification (expected contention answers 503 instead of 500). The shared private-copy inspection makes its private database and WAL copies owner-writable, so on a stable, readable, write-protected installation — including one whose committed content lives only in an uncheckpointed WAL — `sorage preflight` reports its true verdict instead of `unverifiable`, `send --replay-only` returns its normal replay results instead of the inspection refusal, and daemon start admission classifies the installation's real state, with the live installation's files staying byte-identical ([PFL-002](docs/specs/required-specification.md), [PFL-006](docs/specs/required-specification.md), [SND-002](docs/specs/required-specification.md), [CHN-006](docs/specs/required-specification.md)).
- Report committed Handoff outcomes truthfully: `send`, `revise`, and `delete approve` return their committed result with a warning when a post-commit physical activation, unlink, or completion step fails (the pending intent is left to the next process start), every derived inbox-marker refresh warns contained instead of escaping as an untyped failure, Project mutations read their result rows inside the committing transaction so a committed registration can no longer be misreported as an error or a spurious conflict ([SHR-015](docs/specs/required-specification.md), [ADR-0033](docs/architecture-decision-records/README.md#adr-0033-channel-adoption-hardening-and-the-shared-v013-release)).
- Normalize Handoff content references in database schema 9 and Memo references in schema 10 without repacking historical bodies or rewriting retained receipts; the version-11 Channel slot ships as the rebuilt `channels-v2` tables, replaced in place from the unreleased `channels-v1` before first publication with an old development home refused through the existing migration-name check; extend format-3 backups with inline Artifact bodies, selected Memo content files, Channel records and exact digest validation; keep file-backed Artifacts on their existing `artifacts/` paths and omit derived fetch-cache files from backups; restore fresh private records without operational receipts; disclose configured large-content Git-history growth through the CLI and Web guidance.
- Make every Vault-open `VAULT_INTEGRITY_ERROR` state name a safe action that works while the Vault cannot open: inspect the configured `vault.path` and its mount, restore a verified backup into a fresh installation, adopt a foreign Vault only by restoring it into a fresh installation through the audited restore, or backfill an empty directory with `sorage init --reconfigure --non-interactive` only for a genuinely new installation with a confirmed mount. Existing typed refusals keep their codes, exits and details while message and recovery change; a directory listing that fails only when the marker is absent or unreadable now returns `VAULT_INTEGRITY_ERROR`/73 with `{ vaultPath }` instead of `INTERNAL_ERROR`/1 or an untyped failure, without a code-catalogue or HTTP/exit mapping change. Apply the same safe guidance to `sorage doctor`: `vault.marker`, the checksum checks, `home.permissions`, `vault.gitattributes`, `vault.writable` and `platform.tcc` handle Vault-open, configuration-null and earlier-failure branches without naming `sorage vault verify` or `init --reconfigure` unless the Vault opens — a missing policy file or `.gitattributes` line is backfilled by `sorage init --reconfigure --non-interactive`, an existing `.gitignore` without `staging/` needs the named manual edit, and an unreadable or unsafe policy path is repaired instead of reconfigured — and an unreadable configuration or home is an access failure that never suggests initialization. `sorage init` refuses an unreadable, untraversable, or non-regular configuration with the matching access or path repair instead of treating the installation as new. Operational Channel, Handoff and Project commands keep `CONFIG_INVALID`/78 for a configuration they cannot read, and now carry the owner-only access repair — or the configuration-path repair when the path is a directory, a FIFO or another non-regular target, a dangling symlink, or a symlink loop — instead of the `sorage config validate` hint that cannot run in that state; a live symlink to a regular `config.yaml` is still followed on every surface, as before TASK-118. Plain `sorage init` no longer suggests reconfiguration when the configured Vault is missing or unopenable. The section 15 recovery cell, codes, exits and `error-renderings.json` stay unchanged; the section 15 meaning is clarified to scope the default ([VLT-002](docs/specs/required-specification.md), [VLT-003](docs/specs/required-specification.md), [VLT-019](docs/specs/required-specification.md), [INIT-017](docs/specs/required-specification.md)).
- Update the shipped `use-sorage` skill and public and operations guidance: the corrected read and wait wording for the covered zero-write reads, the shared Vault-open and configuration refusal guidance, the write-protected-installation typed refusal and its restore-access recovery, and the shared v0.1.3 upgrade guidance; the EPIC-017 Channel catalog and new-attempt wording are superseded by the EPIC-018 rebuild, whose MCP-first skill and five-step Channel reference are delivered by TASK-125, with the explicit upgrade migration step already applied by TASK-122's operations edit

### Upgrade disclosure

The intended v0.1.3 release carries M8, M9, and the EPIC-017 Channel adoption corrections together under [ADR-0033](docs/architecture-decision-records/README.md#adr-0033-channel-adoption-hardening-and-the-shared-v013-release). The M9 storage upgrade from schema 7 through 11 is one-way for v0.1.2 homes: `sorage preflight` reports `upgrade_required` before the upgrade and `compatible` after it; keep a verified pre-upgrade backup made with the matching old executable and complete its separate restore drill before replacing anything, because older binaries cannot read the upgraded database or format-3 backups. After the upgrade, create the first backup with the new executable and verify it with `sorage backup verify` before running `sorage vault verify`, because that first backup run re-asserts the M9 `.gitattributes` lines that `vault verify` checks. Because covered reads no longer migrate, the procedure names the explicit migration step — run `sorage backup run` once with the new executable after replacement, inside the existing context with scheduling and push disabled, before expecting `preflight` to report `compatible` — which TASK-122 adds to the operations guide in the same change. Rollback means restoring the retained pre-upgrade backup with its matching old executable into a fresh, separate home and Vault through the documented restore drill; operational receipts are excluded by design, and data created after that backup is absent from the restored installation. The EPIC-017 corrections are consolidated in these entries on the qualified source candidate.

These capabilities are implemented in the source candidate for intended v0.1.3; the published v0.1.2 distribution predates them. [The roadmap](docs/roadmap/README.md) owns delivery status, and [the M8 design entrypoints](docs/README.md#m8-design-entrypoints) and [the M9 design entrypoints](docs/README.md#m9-design-entrypoints) define behavior. Installation, consumer activation and publication require separate authorization.

## v0.1.2 - 2026-10-03

This corrected distribution replaces the withdrawn original v0.1.2 distribution dated 2026-09-29. Existing v0.1.2 installations must replace the binary and verify the new release manifest and checksum; the version string remains unchanged.

### Added

- Let the local User create a Handoff from the Web compose form by supplying a Markdown body instead of a file.
- Add `sorage project rebind` to replace a Project directory binding in one command.
- Add durable Project Memos through the CLI, authenticated local HTTP API, Web UI, and shipped `use-sorage` skill with explicit actions and replay-only recovery for uncertain writes.

### Changed

- Let Project archive and unarchive run without `--as-user`, and prevent archived Projects from starting new outgoing Handoffs.
- Export Memo data in format-2 backups while retaining format-1 restore support; before upgrading, stop old writers and keep a verified format-1 backup because older binaries cannot read the new format.

### Fixed

- Allow a registered Git Project to revise a document inside its documented workspace root without an external-source override.
- Preserve multipart Web upload bodies that begin with dashes.
- Keep Handoff sender identity and Project bindings stable when archive or rebind races with a send, and require an explicit override for ancestor-path sends above registered Projects.
- Restore the Web Handoff detail Download action for authenticated sessions.

## v0.1.1 - 2026-09-09

### Added

- Add `sorage review show` and `sorage events` so a session can read the current Review Note and the bounded metadata timeline through the CLI without a daemon.
- Teach requested Handoff processing in the shipped `use-sorage` skill to read the Note with `review show` before `revise`, and keep inbox and outbox checks report-only.

### Changed

- Refresh the Web control plane visual presentation with light and dark design tokens, state badges, census cards, loading and empty states, and grouped detail actions, without changing HTTP endpoints or DTOs.
- Require explicit broker requests for inbox, outbox, and Handoff processing, and default requested project setup to ignore `.sorage/`.
- Pin the required Bun toolchain to `1.4.2`.

### Fixed

- Classify Git password-acquisition failures as authentication errors.
- Correct Web rendering defects found during the visual refresh: invalid button padding, an undefined deleted census card, and an empty artifact revision row.
